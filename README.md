# Спецификация

Сгенерировано из дерева `tests/`, названий тестов и их JSDoc (скилл `spec`, `spec-doc`). Руками не править: правка — в тестах.

## Что делает система

- [ci-wait](capabilities/ci-wait.md) — Скилл `ci-wait`: агент дожидается исхода всех чеков PR или коммита одним скриптом — PASS, FAIL, TIMEOUT или ERROR, — а не угадывает по первому ответу GitHub, что CI прошёл.
- [dashboard](capabilities/dashboard.md) — Скилл `dashboard`: страница в браузере, где по времени видно, сходятся ли оценки задач с фактами и падает ли цена задачи, — чтобы править флоу по цифрам, а не по ощущению.
- [est](capabilities/est.md) — Скилл `est`: сколько часов работы агента займёт задача — по фактам похожих закрытых задач, и сколько заняла на самом деле — часы, токены и стоимость из транскриптов.
- [github-premerge](capabilities/github-premerge.md) — Скилл `github`, `pr premerge`: перед мержем зелёного PR агент проверяет, что он совместим с `main`, который ушёл вперёд после его CI, — и не вливает PR, который сломает `main`.
- [github-project](capabilities/github-project.md) — Скилл `github`, `project check` и `project fix`: проект GitHub любого репозитория устроен одинаково — по канону `AGENTS.md`, и агент приводит его к канону одной командой.
- [github-task](capabilities/github-task.md) — Скилл `github`, `task new`, `task status`, `task actualize`, `task close` и `task drop`: задачу заводят, двигают по доске, закрывают после мержа и снимают одной командой, и она всё время по канону `AGENTS.md`.
- [install](capabilities/install.md) — Установка флоу: одна команда `npx github:miroshnik/ai-dev install` даёт проекту общие правила, справочники и все скиллы последнего релиза ai-dev для любого агента; с `-g` машина получает только скиллы и хук.
- [release](capabilities/release.md) — Релиз ai-dev: владелец одной командой из клона выпускает накопленные правки флоу — тег по дате на `origin/main` и GitHub Release со списком изменений; проекты и машины с копией получают флоу только так.
- [slot](capabilities/slot.md) — Скилл `slot`: тяжёлые прогоны машины — проверки проекта `lint`, `typecheck`, `test` — идут очередью: одновременно два, вместе — половина ядер, остальные ждут по порядку прихода и видят, кого ждут.
- [spec-break](capabilities/spec-break.md) — Проверка решения обязана уметь упасть: `spec-break` доказывает это поломкой — правкой кода, от которой проверка должна покраснеть. Агент выбирает поломку под одну проверку, скрипт применяет её, прогоняет тест и всегда откатывает; ✅ «упал» — проверка ловит эту поломку, ❌ «не упал» — «покрыто» только на словах.
- [spec-claims](capabilities/spec-claims.md) — Нет решения — нет кода: каждая точка входа системы (маршрут, страница, job, команда) вызывается хотя бы одним тестом capability. Код, до которого не доходит ни одно заявленное поведение, — кандидат на удаление или незаписанное требование.
- [spec-diff](capabilities/spec-diff.md) — Скрипт `spec-diff` скилла `spec`: ревьюер PR видит, какие требования PR снимает, меняет и добавляет, — раздел «Спека (тесты)» для тела PR с названиями тестов.
- [spec-doc](capabilities/spec-doc.md) — Скрипт `spec-doc` скилла `spec`: документация `docs/spec` из тестов — страница на capability, правило архитектуры и стандарт, которая читается рассказом: зачем, что умеет, чем проверено.
- [spec-exceptions](capabilities/spec-exceptions.md) — Исключения решения живут файлом на элемент — `exceptions/<элемент>.json` в папке решения, а не массивом в `exceptions.ts`: подзадачи разбора долга параллельно убирают каждая своё исключение, и в общем массиве каждая следующая получала конфликт соседних строк и повторный прогон CI. Удаление своего файла ни с чем не пересекается.
- [spec-harness](capabilities/spec-harness.md) — Харнесс проверок скилла `spec`: соглашение о коде или поведении проекта проверяется механически, а тесты проверки попадают в отчёт раннера и в спеку так же, как обычные.
- [spec-publish](capabilities/spec-publish.md) — Скрипт `spec-publish` скилла `spec`: после мержа в `main` CI публикует сгенерированную документацию `docs/spec` в отдельную ветку `spec`, а не коммитит её в `main`.
- [update](capabilities/update.md) — Проверка и обновление флоу: агент первым шагом сессии узнаёт, не отстали ли правила и скиллы от последнего релиза ai-dev, и одной командой доводит их до актуальных — чтобы сессия работала по текущим правилам, а не по когда-то поставленным.

## Каким правилам подчиняется код

- [canon-size](standards/canon-size.md) — Ядро канона (`AGENTS.md`, у Claude Code ещё `claude/CLAUDE.md`) грузится в контекст на старте каждой сессии и каждого субагента и заново читается на каждом ходу; 99 % токенов сессии — это чтение кэша. Поэтому у ядра есть бюджет: `AGENTS.md` ≤ 32 КиБ, `claude/CLAUDE.md` ≤ 5 КиБ. Справочное — как писать спеку, как устроен проект GitHub, фрагменты CI — живёт там, где его читают по делу (скиллы, `docs/`), а ядро называет, куда идти.
- [cloud-session](standards/cloud-session.md) — Скрипты скиллов, которые ходят в GitHub Projects, в облачной сессии выходят с объяснением, а не сбоем `gh`.
- [config-dir](standards/config-dir.md) — Каталог личной конфигурации — `$AI_DEV_CONFIG_DIR`, иначе `~/.config/ai-dev` — каждый скрипт вычисляет одним и тем же выражением, поэтому скиллы видят одни и те же файлы.
- [exception-files](standards/exception-files.md) — Файл исключений папки решения (канон spec: «Исключения — только в `exceptions/` папки решения») каждый скрипт распознаёт одинаково: на вопрос «файл исключений какой папки решения?» харнесс, `spec-doc`, `spec-diff` и `spec-exceptions` отвечают одно и то же, `github pr labels` по тому же ответу решает, механическая ли правка.
- [harness-load](standards/harness-load.md) — Харнесс и модель архитектуры скилла `spec` импортирует тест проекта любым раннером — и тем, что грузит TypeScript как CommonJS: Playwright и Jest в проекте без `"type": "module"`.
- [node-runtime](standards/node-runtime.md) — Скрипты скилла `spec` идут под Node ≥ 22.18 без Bun — CI проекта на Node запускает их из копии скилла в проекте.
- [readme](standards/readme.md) — README — витрина флоу для того, кто видит репозиторий впервые, и он не отстаёт от флоу: называет каждый скилл, каждую команду установщика и скиллов с её подкомандами, каждый справочник `docs/`, а его ссылки и якоря ведут на существующее.
- [spawn-no-jit](standards/spawn-no-jit.md) — Тест, который запускает bun, на macOS запускает его без JIT (`BUN_JSC_useJIT=0`), — чтобы крэш macOS 27 при старте процесса не ронял случайный зелёный тест.
- [spawn-timeout](standards/spawn-timeout.md) — Тест, который запускает процессы (git, node, bun), держит таймаут `SPAWN_TIMEOUT`, а не 5 с bun по умолчанию, — чтобы нагрузка машины не роняла зелёные тесты.
- [task-branch](standards/task-branch.md) — Ветку задачи `<type>/<N>-<slug>` (AGENTS.md, «Сессия и ветка») каждый скилл разбирает одинаково: на вопрос «ветка задачи N?» `est` и `github` отвечают одно и то же.
