# Спецификация

Сгенерировано из дерева `tests/`, названий тестов и их JSDoc (скилл `spec`, `spec-doc`). Руками не править: правка — в тестах.

## Что делает система

- [agent-shell](capabilities/agent-shell.md) — Bash-вызов агента в Claude Code понимает команды, написанные для bash: глоб без совпадений уходит команде как есть, `====` и `==` — просто символы, `timeout` есть и там, где его нет у машины. Настраивает это хук `SessionStart`, который ставит `install -g`, — механикой, а не абзацем правил.
- [ci-wait](capabilities/ci-wait.md) — Скилл `ci-wait`: агент дожидается исхода всех чеков PR или коммита одним скриптом — PASS, FAIL, TIMEOUT или ERROR, — а не угадывает по первому ответу GitHub, что CI прошёл.
- [dashboard](capabilities/dashboard.md) — Скилл `dashboard`: страница в браузере, где по времени видно, сходятся ли оценки задач с фактами и падает ли цена задачи, — чтобы править флоу по цифрам, а не по ощущению.
- [est](capabilities/est.md) — Скилл `est`: сколько часов работы агента займёт задача — по фактам похожих закрытых задач, и сколько заняла на самом деле — часы, токены и стоимость из транскриптов.
- [github-premerge](capabilities/github-premerge.md) — Скилл `github`, `pr premerge`: перед мержем зелёного PR агент проверяет, что он совместим с `main`, который ушёл вперёд после его CI, — и не вливает PR, который сломает `main`.
- [github-project](capabilities/github-project.md) — Скилл `github`, `project check` и `project fix`: проект GitHub любого репозитория устроен одинаково — по канону `AGENTS.md`, и агент приводит его к канону одной командой.
- [github-task](capabilities/github-task.md) — Скилл `github`, `task new`, `task show`, `task answer`, `task status`, `task actualize`, `task close`, `task resume`, `task queue` и `task drop`: задачу заводят, читают, отвечают на её вопросы, двигают по доске, закрывают после мержа и снимают одной командой, и она всё время по канону `AGENTS.md`.
- [install](capabilities/install.md) — Установка флоу: одна команда `bunx @miroshnik/elves install` ставит проекту флоу последнего релиза Elves для любого агента — тонким, без копии; с `-g` машина получает канон, скиллы и хук.
- [release](capabilities/release.md) — Релиз Elves: владелец одной командой из клона выпускает накопленные правки флоу — тег по дате на `origin/main` и GitHub Release со списком изменений; проекты и машины с копией получают флоу только так.
- [slot](capabilities/slot.md) — Скилл `slot`: тяжёлые прогоны машины — проверки проекта `lint`, `typecheck`, `test` — идут очередью: одновременно два, вместе — половина ядер, остальные ждут по порядку прихода и видят, кого ждут.
- [spec-break](capabilities/spec-break.md) — Проверка решения обязана уметь упасть: `spec-break` доказывает это поломкой — правкой кода, от которой проверка должна покраснеть. Агент выбирает поломку под одну проверку, скрипт применяет её, прогоняет тест и всегда откатывает; ✅ «упал» — проверка ловит эту поломку, ❌ «не упал» — «покрыто» только на словах.
- [spec-claims](capabilities/spec-claims.md) — Нет решения — нет кода: каждая точка входа системы (маршрут, страница, job, команда) вызывается хотя бы одним тестом capability. Код, до которого не доходит ни одно заявленное поведение, — кандидат на удаление или незаписанное требование.
- [spec-diff](capabilities/spec-diff.md) — Скрипт `spec-diff` скилла `spec`: ревьюер PR видит, какие требования PR снимает, меняет и добавляет, — раздел «Спека (тесты)» для тела PR с названиями тестов.
- [spec-doc](capabilities/spec-doc.md) — Скрипт `spec-doc` скилла `spec`: документация `docs/spec` из тестов — страница на capability, правило архитектуры и стандарт, которая читается рассказом: зачем, что умеет, чем проверено.
- [spec-exceptions](capabilities/spec-exceptions.md) — Исключения решения живут файлом на элемент — `exceptions/<элемент>.json` в папке решения, а не массивом в `exceptions.ts`: подзадачи разбора долга параллельно убирают каждая своё исключение, и в общем массиве каждая следующая получала конфликт соседних строк и повторный прогон CI. Удаление своего файла ни с чем не пересекается.
- [spec-harness](capabilities/spec-harness.md) — Харнесс проверок скилла `spec`: соглашение о коде или поведении проекта проверяется механически, а тесты проверки попадают в отчёт раннера и в спеку так же, как обычные.
- [spec-publish](capabilities/spec-publish.md) — Скрипт `spec-publish` скилла `spec`: после мержа в `main` CI публикует сгенерированную документацию `docs/spec` в отдельную ветку `spec`, а не коммитит её в `main`.
- [spec-shard](capabilities/spec-shard.md) — Скрипт `spec-shard` скилла `spec`: шард CI получает тестовые файлы по длительностям прошлого зелёного прогона, а не по числу тестов.
- [task-env](capabilities/task-env.md) — Скилл `task-env`: у задачи #N свой стек Docker Compose — проект Compose `<проект>-<N>` (эпик #392), — у приложений задачи свои адреса `<сервис>.<N>.<проект>.localhost` — их раздаёт один на машину прокси Traefik по меткам контейнеров, а `check -g` говорит, работает ли он; `check` проекта держит compose-файл правил изоляции стеков задач; `task-env up`, `e2e` и `down` поднимают, пересоздают для прогона и снимают стеки задачи по её номеру, а compose-файл получает адреса стека в `TASK_ENV_<СЕРВИС>_URL`; `task close` снимает стеки сам, а `prune` находит и снимает стеки закрытых задач.
- [update](capabilities/update.md) — Проверка и обновление флоу: агент первым шагом сессии узнаёт, не отстали ли правила и скиллы от последнего релиза Elves, и одной командой доводит их до актуальных — чтобы сессия работала по текущим правилам, а не по когда-то поставленным.

## Каким правилам подчиняется код

- [artifact-hidden-files](standards/artifact-hidden-files.md) — Шаг `actions/upload-artifact`, чей путь скрытый — файл или каталог с точкой в начале имени (`.spec-*.json`, `.spec-journal/`), — стоит с `include-hidden-files: true`. С v4.4 действие по умолчанию пропускает скрытые файлы: без флага артефакт выходит пустым, шаг лишь предупреждает «No files were found», а падает следующая job — на `download-artifact` — или идёт без отчёта.
- [canon-size](standards/canon-size.md) — Ядро канона (`AGENTS.md`, у Claude Code ещё `claude/CLAUDE.md`) грузится в контекст на старте каждой сессии и каждого субагента и заново читается на каждом ходу; 99 % токенов сессии — это чтение кэша. `SKILL.md` агент читает при каждом вызове скилла — по замерам сессий в проектах (эпик #428) медиана 8 раз за сессию, а описание скилла стоит в списке скиллов каждой сессии. Поэтому у них бюджет в словах: `AGENTS.md` ≤ 3 000, `claude/CLAUDE.md` ≤ 700, каждый `SKILL.md` ≤ 2 500, описание скилла (`description` во frontmatter) ≤ 1 024 символов. Справочное — как писать спеку, как устроен проект GitHub, флаги команд — живёт там, где его читают по делу: `reference.md` скилла, `--help` скрипта, `docs/`; ядро и `SKILL.md` называют, когда и что звать и куда идти.
- [check-run-state](standards/check-run-state.md) — Состояние check-run головы PR `github` и `ci-wait` читают одинаково: на вопрос «какое состояние у чека `<имя>`» по его check-runs — status, conclusion и перезапуски — оба скрипта отвечают по одной таблице, а запросы `github` берут чеки головы одним фрагментом.
- [ci-concurrency](standards/ci-concurrency.md) — Блок `concurrency` с общей группой — не своей у PR или прогона — стоит с `queue: max`: иначе GitHub держит в группе один ожидающий прогон и вытесняет его следующим, и прогон `main` получает статус cancelled.
- [cli-help](standards/cli-help.md) — Скрипт флоу — установщик `elves` и исполняемый скрипт скилла — отвечает на `--help` и `-h` и у себя, и у каждой своей команды: синтаксис и один-два примера в stdout, код 0, без сети, без внешних команд и без записи файлов.
- [cloud-session](standards/cloud-session.md) — Скрипты скиллов, которые ходят в GitHub Projects, в облачной сессии выходят с объяснением, а не сбоем `gh`.
- [config-dir](standards/config-dir.md) — Каталог личной конфигурации — `$ELVES_CONFIG_DIR`, иначе `~/.config/elves` — каждый скрипт вычисляет одним и тем же выражением, поэтому скиллы видят одни и те же файлы.
- [exception-files](standards/exception-files.md) — Файл исключений папки решения (канон spec: «Исключения — только в `exceptions/` папки решения») каждый скрипт распознаёт одинаково: на вопрос «файл исключений какой папки решения?» харнесс, `spec-diff` и `spec-exceptions` отвечают одно и то же, `github pr labels` по тому же ответу решает, механическая ли правка.
- [fast-tests](standards/fast-tests.md) — Локальный `test` — быстрый уровень: тесты, которым нужен Docker, живой сервер или сеть corepack, лежат в файлах `*.slow.test.ts` и идут скриптом `test:slow`, CI гоняет оба уровня; повторы `gh` в тестах — без настоящих пауз.
- [flow-english](standards/flow-english.md) — Флоу — канон, справочники, скиллы и README — пишется по-английски: репозиторий публичный, а агент работает с человеком на языке проекта (`language` в `.agents/elves.json`, capability `install`). Поэтому в документах флоу нет кириллицы — ни в прозе, ни в цитатах вывода скриптов, ни в путях и плейсхолдерах. Под правило попадает и `package.json`: его описание показывают npm и npx.
- [harness-load](standards/harness-load.md) — Харнесс и модель архитектуры скилла `spec` импортирует тест проекта любым раннером — и тем, что грузит TypeScript как CommonJS: Playwright и Jest в проекте без `"type": "module"`.
- [no-env-file](standards/no-env-file.md) — Скрипт флоу под `bun` идёт с `--no-env-file`: env-файлы проекта — `.env`, `.env.<NODE_ENV>`, `.env.local` — в его окружение не попадают и дальше командам не передаются.
- [old-name](standards/old-name.md) — Флоу переименован в Elves (эпик #542), а установки переходят по одной: проект с копией прошлого релиза, машина до `update -g`, профиль владельца с переменной `AI_DEV_*`. Поэтому старое имя `ai-dev` (и `AI_DEV_*`) в файлах флоу остаётся только там, где оно читается для перехода, — и решение там одно: старое имя узнаётся своим и заменяется новым, второго нет. Манифест `update` переносит, а не копирует; блок в `AGENTS.md` заменяет на месте; хук со старой командой узнаёт своим и не ставит второй; скрипт до переноса читает прежний манифест, но новый, если есть, — первым.
- [origin-repo](standards/origin-repo.md) — Репозиторий чекаута `owner/repo` по URL его `origin` каждый скилл определяет одинаково: на вопросы «какой это репозиторий?» и «это чекаут репозитория X?» `est`, `github` и `task-env` отвечают одно и то же.
- [package-manager](standards/package-manager.md) — Менеджер пакетов проекта во флоу определяет одна функция: на вопрос «какой менеджер пакетов у проекта» отвечает `packageManager(dir)` скилла `github` по одной таблице случаев, а `pr premerge`, обёртка slot и раннер готовой строки `test:spec` у `check` берут ответ у неё.
- [readme](standards/readme.md) — README — витрина флоу для того, кто видит репозиторий впервые, и он не отстаёт от флоу: называет каждый скилл, каждую команду установщика и скиллов с её подкомандами, каждый справочник `docs/`, а его ссылки и якоря ведут на существующее.
- [section-refs](standards/section-refs.md) — Ссылка на раздел документа флоу по названию — `AGENTS.md, «First step of a session»` в выводе установщика, `SKILL.md, «Cloud session»` в предупреждении `est`, `` `AGENTS.md`, "Task tracking" `` в справочнике — ведёт на существующий заголовок.
- [session-pin](standards/session-pin.md) — Закрепление задачи за сессией — файл `sessions/<id сессии>` в каталоге личной конфигурации (стандарт `config-dir`) со строкой `owner/repo#N` — каждый скилл разбирает одинаково: на вопрос «за какой задачей эта сессия?» `github`, `est` и `dashboard` отвечают одно и то же.
- [skill-imports](standards/skill-imports.md) — Скрипт скилла импортирует код другого скилла только по списку зависимостей стандарта: на вопрос «без какого соседа скилл не загрузится?» отвечает список, и импорт вне списка не проходит.
- [spawn-no-jit](standards/spawn-no-jit.md) — Тест, который запускает bun, на macOS запускает его без JIT (`BUN_JSC_useJIT=0`), — чтобы крэш macOS 27 при старте процесса не ронял случайный зелёный тест.
- [spawn-timeout](standards/spawn-timeout.md) — Тест, который запускает процессы (git, node, bun), держит таймаут `SPAWN_TIMEOUT`, а не 5 с bun по умолчанию, — чтобы нагрузка машины не роняла зелёные тесты.
- [spec-publish-job](standards/spec-publish-job.md) — Публикацию спеки среди чеков `github` и `ci-wait` узнают одинаково: на вопрос «check-run `<имя>` — публикация спеки?» оба скрипта отвечают по одной таблице, а job публикации во фрагментах CI скилла `spec` и в CI Elves назван так, что правило его узнаёт.
- [task-branch](standards/task-branch.md) — Ветку задачи `<type>/<N>-<slug>` (AGENTS.md, «Session and branch») каждый скилл разбирает одинаково: на вопрос «ветка задачи N?» `est`, `github` и `task-env` отвечают одно и то же.
