# est — оценка по истории, факт по транскриптам

Оценка «из головы» ничем не проверяема. Здесь оценка выводится из фактов по
уже закрытым задачам, а факт измеряется по транскриптам Claude Code, а не
сообщается по памяти. Скрипт `scripts/est.py` делает всё детерминированное
(транскрипты, GraphQL, поля проекта, комментарии); за агентом — выбор
аналогов и объяснение причин.

**Единица:** «Оценка, ч» = «Факт, ч» = активные часы в Claude Code по задаче
(работа агента + паузы ≤ 30 мин между записями). Не человеко-часы, не
календарь. Ручную работу вне Claude человек дописывает сам строкой
«+ вручную: N ч» в комментарий «Факт».

Запуск: `python3 ${CLAUDE_SKILL_DIR}/scripts/est.py <подкоманда> …`
(ниже сокращённо `est`). `--repo owner/repo` можно опустить, если работаешь в
каталоге репозитория. Реестр репозиториев (какие есть, где лежат локально,
номер проекта) — личный файл `~/.claude/est/repos.json`, в скилл не входит;
формат описан в начале `est.py`. Без записи в реестре скрипт определяет репо
по `git remote origin`, а проект — по привязке к репозиторию.

## Когда что запускать

| Момент | Действие |
|---|---|
| Создаёшь маленькую задачу или подзадачу эпика | процедура «Оценка» ниже |
| PR смёржен / issue закрыт | `est fact <N> --write` |
| Перед любой оценкой, раз в сессию | `est fact --sweep --since 90d --write` — добить факты закрытым |
| Спрашивают про точность / историю | `est history [--grep слово]` |

Эпик отдельно не оценивается: его «Оценка, ч» и «Факт, ч» — сумма подзадач
(`est fact <эпик>` сам суммирует и говорит, у скольких подзадач факта нет).

## Оценка новой задачи

1. `est fact --repo <r> --sweep --since 90d --write` — история должна быть
   актуальной; это 10–60 с.
2. `est history --repo <r> [--grep <слово>]` — таблица закрытых задач с
   фактом и текущий k. Если пусто — `est history --all-repos`.
3. Выбери 2–3 аналога. Порядок признаков: те же метки → тот же тип
   (feat / fix / docs / refactor / perf / test / chore / ci / build /
   research — как префикс ветки) → та же подсистема по словам
   заголовка → **похожий объём**. Тема без объёма — плохой аналог: при
   сомнении посмотри `gh issue view <k> --json body,closedByPullRequestsReferences`
   и `gh pr view <pr> --json additions,deletions,changedFiles`. Дифф — признак
   размера, не времени, но отсеивает несопоставимое.
4. База = медиана фактов аналогов. Поправка на названное отличие — только
   ×0,5 / ×1 / ×1,5 / ×2, с причиной в одну фразу. Факты аналогов расходятся
   больше чем в 3 раза — в комментарий диапазон, в поле верхняя граница.
5. k (факт/оценка по истории) скрипт применяет сам по правилу: n < 5 — нет;
   5–9 — если |k−1| ≥ 0,25; ≥ 10 — всегда; k вне 0,5…3 — не применяет и
   предупреждает, что процедура сломана (тогда разберись, почему).
6. Округли к шкале 0,5 · 1 · 2 · 3 · 5 · 8 · 13 · 20 ч. Больше 13 ч — не
   оценивать, разбить на подзадачи.
7. Запиши:
   `est estimate <N> --repo <r> --hours 3 --type feat --analogs 254,260 --mult 1 --note "объём тот же" --write`
   Скрипт ставит поле «Оценка, ч» и пишет комментарий вида
   `Оценка: 3 ч (тип feat, доверие B). Аналоги: #254 (факт 2 ч), #260 (4,5 ч). Поправка: ×1 (объём тот же). k=1,1 (n=12, применён).`

Доверие: A — ≥ 5 аналогов того же типа с фактом в этом репо и k применён;
B — 2–3 аналога; C — аналогов нет.

**Холодный старт — честно.** В репо < 2 фактов → аналоги из других репо
(`--all-repos`), в комментарии «Аналоги из проекта …». Фактов нет нигде →
`--analogs` не передавать, в комментарии будет «Аналоги: нет, оценка
экспертная», доверие C, только шкала. Никаких «стартовых ставок за
операцию» — это выдуманная точность.

**После начала работы оценку не переписывать.** Расхождение объясняется в
комментарии «Факт», факт сравнивается с той оценкой, что стоит в поле.

## Факт при закрытии

Сразу после мержа PR (или закрытия issue без PR):

```bash
est fact <N> --repo <r> --write
```

Скрипт находит сессии задачи (по хешам коммитов PR в выводах инструментов,
записям `pr-link`, ветке с номером задачи, `#N` в первом промпте сессии или в
задании субагенту), считает активные часы — включая работу субагентов и
workflow внутри сессии — и пишет комментарий:

`Факт: 3,1 ч активных в Claude Code (оценка 3 ч, ×1,03). 2 сессии, 14 промптов, стена 10,2 ч, покрытие full. PR #336; 8 коммитов, дифф 2140 строк.`

плюс поле «Факт, ч». Покрытие: `full` — все PR задачи видны в транскриптах;
`partial` — часть работы прошла мимо Claude Code (второй разработчик, другой
инструмент); `none` — сессий нет, поле не ставится, в комментарии «факт
недоступен». В k и в аналоги идут только `full`. Не дописывай цифру на глаз,
если скрипт факта не нашёл — «нет данных» ценнее выдуманного числа.

Если факт/оценка вне ×0,5…×2 и оценка ≥ 2 ч — добавь в тот же комментарий
строку `Причина: <пропущена работа | вырос объём | внешний блокер | неверный аналог | иное>: <1–2 предложения>`
(скрипт при повторном запуске эту строку сохраняет).

Задачи «не будем делать» и дубли факта не получают (их в проекте уже нет).

## Чтобы факт находился — привязка работы к задаче

Без этого покрытие будет `partial`/`none`, и история не накопится:

- одна сессия — одна задача; ветка по конвенции `<type>/<issue>-<slug>`
  (`feat/263-rakeback-claim-history`, допустим префикс области
  `backend/fix/263-…`; старое `issue-263-…` тоже распознаётся) — из неё
  скрипт берёт и номер задачи, и тип для истории;
- номер задачи (`#263` или ссылка) — в первом промпте сессии **и в задании
  каждому субагенту / агенту workflow**, который делает эту задачу: транскрипты
  субагентов считаются частью сессии, и по номеру в задании их работа
  привязывается к своей задаче даже когда несколько задач идут параллельно
  (без номера параллельная работа делится по порядку коммитов — грубо);
- в теле PR — `Closes #263`;
- коммитить логическими шагами, не одним коммитом на PR;
- в репо, где задачи закрывают коммитами без PR, — `Closes #N` в сообщении
  коммита.

## Справочник команд

```bash
est history [--repo o/r] [--grep СЛОВО] [--all-repos] [--last N]
est fact <N> [--repo o/r] [--write] [--gap 30] [--json]
est fact --sweep [--since 90d] [--repo o/r] [--write]
est estimate <N> [--repo o/r] --hours H --type <type> \
    [--analogs a,b[,c]] [--mult 0.5|1|1.5|2] [--note "причина"] [--write]
# <type> — как префикс ветки: feat fix docs refactor perf test chore ci build research
```

Без `--write` всё только печатается — так можно проверить, что скрипт нашёл,
прежде чем писать в GitHub. Комментарии идемпотентны: маркеры
`<!-- est {…} -->` и `<!-- fact {…} -->` в конце комментария, повторный
запуск обновляет существующий, а не плодит новые. `--sweep --write` пишет
только задачи с покрытием `full`/`partial` — «недоступен» массово не
рассылает; для одной задачи `est fact <N> --write` запись «факт недоступен»
делает (это и есть честная запись при закрытии).

Номер — это номер **issue**, не PR: на номер PR скрипт предупредит и посчитает
факт по самому PR. Общий коммит/PR, закрывший несколько задач, делится между
ними поровну (в комментарии видно «без деления: N ч»).

## Подводные камни

- Поля проекта ищутся по точному имени через GraphQL; в JSON
  `gh project item-list` ключи кириллических полей искажены — не полагайся
  на них.
- Транскрипты живут в `~/.claude/projects/<путь-через-дефисы>*/` и
  чистятся через `cleanupPeriodDays` (в `settings.json` должно быть 365).
  Комментарий «Факт» и поле — уже архив результата; транскрипты нужны
  только для пересчёта.
- Сессии с < 3 промптами без PR и коммитов (автоматические рутины) скрипт
  пропускает; если факт у задачи подозрительно мал — проверь, не была ли
  работа в такой сессии или в чужой ветке.
- Старые оценки без маркера `<!-- est -->` (поставленные до внедрения `est`,
  обычно в человеко-часах) в k не участвуют — единица другая.
