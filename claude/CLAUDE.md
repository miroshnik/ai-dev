# Общие правила для всех проектов

## Этот файл и скиллы

Живут в репозитории **miroshnik/ai-dev** (`~/Projects/ai-dev`): `claude/CLAUDE.md`
и `claude/skills/*`; в `~/.claude` — симлинки на них (`install.sh`). Правишь
правила или скилл — сразу же коммить и пуш в ai-dev
(`git -C ~/Projects/ai-dev add -A && git commit && git push`), это не требует
отдельной просьбы. Задачи по правилам и скиллам — в issues ai-dev, проект
`ai-dev` (#6).

**Репозиторий публичный.** В нём — только общие правила и скиллы. Никаких
названий, владельцев, путей и номеров проектов других репозиториев, имён
коллег и заказчиков — ни в файлах, ни в истории git, ни в issues и
комментариях ai-dev. Примеры в правилах — вымышленные. Личная конфигурация
(какие репозитории есть, где лежат, номера проектов) живёт только локально
в `~/.claude` (например, реестр `~/.claude/est/repos.json`) и в памяти Claude.

**Скилл = промпт + скрипты**, по документации Claude Code: папка
`claude/skills/<name>/` с `SKILL.md` (frontmatter `name`, `description`,
`when_to_use`, `argument-hint`, `allowed-tools`; тело < 500 строк) и
`scripts/` для детерминированной части; при необходимости `reference.md`.
Всё, что зависит от конкретных репозиториев, — в локальную конфигурацию, не
в скилл.

Помни: глобальный CLAUDE.md читают и автономные рутины (scheduled-задачи
Claude) — правка действует на них немедленно.

## Ведение задач

- Задачи ведём в **GitHub Issues** репозитория проекта (`gh issue ...`), а не в
  локальных списках, TODO-файлах или TaskList.
- Всё пишем **на русском**: заголовки, описания, комментарии, чек-листы.
- **Маленькая задача** — один issue.
- **Большая задача** — эпик + подзадачи:
  - эпик — отдельный issue с **типом issue «Эпик»** (Issue type, не метка):
    цель, контекст, план (по этапам, если они есть), критерии готовности.
    Тип заводится один раз на организацию
    (`gh api orgs/<org>/issue-types -f name=Эпик -f color=purple -F is_enabled=true`),
    ставится `gh api -X PATCH repos/{owner}/{repo}/issues/<N> -f type=Эпик`
    (или `gh issue create … --type Эпик`); поиск —
    `gh issue list --json number,issueType --jq '.[]|select(.issueType.name=="Эпик")'`.
    В репозиториях личного аккаунта типов нет — там эпик помечаем меткой
    `epic`, это единственное исключение;
  - у эпика есть **короткий префикс** (`Биллинг`, `Импорт`, `API`): с него
    начинаются заголовки эпика и всех его подзадач (`<Префикс> · <заголовок>`),
    он же идёт в названия milestones;
  - каждая подзадача — отдельный issue, привязанный к эпику как **sub-issue**
    (нативные sub-issues GitHub);
  - подзадача должна быть законченной единицей работы, которую можно сделать
    одним PR;
  - эпик может разбить план на этапы — тогда этап это milestone (раздел
    ниже) и каждая подзадача принадлежит одному этапу; эпик без этапов —
    без milestones.
- **Зависимости — только встроенными связями GitHub** (Relationships), не
  текстом в описании: родитель — sub-issue (эпик), «блокируется» —
  *blocked by*, «блокирует» — *blocking*. Разделов «Зависит от» / «После #N»
  в описании не пишем; если зависимость не issue (ответ заказчика, внешний
  срок) — заводим под неё задачу или пишем в «Контекст», не как зависимость.
  *Relates to* через API не ставится — только в UI, и только если связь не
  «блокирует». Задача с непустым *blocked by* не берётся в работу, пока
  блокеры не закрыты.

  ```bash
  # id (не номер!) блокирующей задачи
  BY_ID=$(gh api repos/{owner}/{repo}/issues/<блокер> --jq .id)
  gh api repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by -X POST -F issue_id=$BY_ID
  gh api repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by          # кто блокирует N
  gh api repos/{owner}/{repo}/issues/<N>/dependencies/blocking            # кого блокирует N
  gh api -X DELETE repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by/$BY_ID
  ```
- Перед созданием новой задачи проверяем, нет ли уже такой (`gh issue list --search`).
- Статус ведём только в поле `Status` проекта (раздел ниже), в самом issue
  ничего не дублируем; PR связываем с задачей (`Closes #N`); эпик закрываем,
  когда закрыты все подзадачи.
- Если у проекта нет GitHub-репозитория — сказать об этом и спросить, где вести
  задачи, а не заводить их молча в другом месте.

### Проект (GitHub Projects)

У каждого репозитория есть **ровно один** GitHub Project, привязанный к репо
(`gh project link`); название проекта = имя репозитория. В нём **все** эпики и
задачи репозитория — отдельных проектов под эпик/направление не заводим
(направление = эпик внутри общего проекта). Все задачи (эпики и подзадачи)
добавляются в проект сразу при создании. Обязательно в проекте:

- **Три представления**, ровно с такими именами:
  - `Доска` (BOARD_LAYOUT) — колонки по полю `Status` (это дефолт доски;
    группировка через API не настраивается);
  - `Таблица` (TABLE_LAYOUT);
  - `Роадмэп` (ROADMAP_LAYOUT) — поля дат и маркеры milestones у роадмэпа
    через API не задаются: после создания попросить пользователя один раз
    настроить их в UI.
- **Поле `Status`** с вариантами: `Бэклог` → `В работе` → `Готово`.
  Статус меняю **сам, сразу**, не дожидаясь просьбы:
  - новая задача — при создании ставлю `Бэклог`;
  - взял задачу в работу — до начала работы ставлю `В работе`;
  - закончил (PR смёржен / задача закрыта) — ставлю `Готово`;
  - задачу переоткрыли (баг вернулся, PR откатили) — возвращаю `В работе`
    (или `Бэклог`, если работа не ведётся); уже закрытые milestone и эпик
    при этом переоткрываю;
  - **закрыта без выполнения** (не будем делать, дубль, заменена другими
    задачами) — закрываю `gh issue close <N> --reason "not planned"` и
    **убираю из проекта** (`gh project item-delete`): в `Готово` она не
    попадает, в оценке эпика не считается.
  Эпик: `В работе`, когда взята первая подзадача; `Готово`, когда готовы все
  (закрытые как not planned не в счёт — их в проекте уже нет).
- **Поле `Оценка, ч`** (тип Number) — оценка в активных часах Claude Code
  (раздел «Оценка и факт»). Ставится **только через скилл `est`** — по
  аналогам с фактом, не из головы. Заполняется у каждой подзадачи и маленькой
  задачи при создании; у эпика — сумма оценок подзадач, пересчитываю её при
  добавлении подзадачи или изменении её оценки. После начала работы оценку
  не переписываю — расхождение объясняется в комментарии «Факт».
- **Поле `Факт, ч`** (тип Number) — фактические активные часы; заполняет
  только скрипт скилла `est` при закрытии задачи, руками не трогать.

Кроме перечисленного, в проекте ничего лишнего: никаких дополнительных полей
(Iteration, Приоритет, Готовность и т.п.) и представлений сверх трёх
перечисленных, пока их не внесли в эти соглашения. В частности:

- **Приоритет** — это ручной порядок карточек в проекте (выше = важнее),
  отдельного поля нет. Новую задачу ставим в конец `Бэклога`; переставляем —
  `updateProjectV2ItemPosition`.
- **Готовность / «можно ли начинать»** — выражается статусом, отдельного поля
  нет.
- **Этапы / фазы** — встроенные **milestones** репозитория (раздел ниже), а
  не своё поле в проекте; в проекте они видны через встроенное поле `Milestone`.

Перед работой с задачами проверить, что проект есть и соответствует этому
описанию. Без проекта статусы вести негде, поэтому если проекта нет — создать
его сразу, а если не хватает полей/статусов/представлений — донастроить
(сообщить, что сделал). Удалять или переименовывать что-то в проекте, которым
уже пользовались, — только после подтверждения.

```bash
# проверка: проект привязан к репо? какие представления? какие поля?
gh api graphql -f query='{repository(owner:"<owner>",name:"<repo>"){projectsV2(first:5){nodes{number title}}}}'
gh api graphql -f query='{organization(login:"<owner>"){projectV2(number:<N>){views(first:10){nodes{id name layout}}}}}'   # для личного аккаунта — user(login:)
gh project field-list <N> --owner <owner> --format json
```

Создание с нуля:
- проще всего скопировать уже настроенный проект:
  `copyProjectV2(input:{projectId, ownerId, title:"<repo>"})` (`ownerId` —
  node ID владельца: `{organization(login:"…"){id}}` или `{viewer{id}}`);
  представления и поля скопируются, задачи — нет. Если копировать нечего —
  `gh project create --owner <owner> --title "<repo>"`;
- привязать к репо: `gh project link <N> --owner <owner> --repo <owner>/<repo>`;
- у свежесозданного проекта уже есть поле `Status` (`Todo / In Progress /
  Done`) и представление `View 1`. Варианты `Status` не добавляю, а **заменяю
  целиком** (`color` и `description` обязательны):
  `updateProjectV2Field(input:{fieldId:"…",singleSelectOptions:[{name:"Бэклог",color:GRAY,description:""},{name:"В работе",color:YELLOW,description:""},{name:"Готово",color:GREEN,description:""}]})`.
  `View 1` переименовываю в `Таблица` (`updateProjectV2View(input:{viewId,name})`),
  `Доска` и `Роадмэп` создаю: `createProjectV2View(input:{projectId,name,layout:BOARD_LAYOUT})`
  / `ROADMAP_LAYOUT`;
- поле оценки: `gh project field-create <N> --owner <owner> --name "Оценка, ч" --data-type NUMBER`.

```bash
# добавить issue в проект и проставить поля
ITEM=$(gh project item-add <N> --owner <owner> --url <issue-url> --format json --jq .id)
gh project item-edit --id $ITEM --project-id <project-id> --field-id <id-поля-Оценка> --number 4
gh project item-edit --id $ITEM --project-id <project-id> --field-id <id-поля-Status> --single-select-option-id <id-варианта>
```

ID проекта, полей и вариантов: `gh project view <N> --owner <owner> --format json`,
`gh project field-list <N> --owner <owner> --format json`.

### Milestones — наборы задач

Milestone (встроенная сущность репозитория) — это **просто именованный набор
задач** с общей целью и, если есть, сроком. Ничего другого для группировки
(спринты, своё поле «Этап»/«Фаза»/«Релиз» в проекте) не используем. Что
кладём в один milestone — решает смысл, а не структура:

- несколько простых задач (`Релиз 2026-10`, `Демо для бизнеса`);
- несколько эпиков целиком — тогда milestone стоит у самих эпиков;
- **этап эпика** — набор его подзадач; так эпик использует milestones как
  этапы.

Правила:

- **Не обязателен** — ни задаче, ни эпику. Заводим, только когда группу
  задач надо отслеживать как целое (общий результат или срок). Эпик без плана
  по этапам — без milestones, его подзадачи без milestone.
- **Название.** Этап эпика: `<Эпик> · <N> · <Название этапа>`
  (`Биллинг · 1 · Модель данных`, `Импорт · 0 · Исправления без решений бизнеса`),
  где `<Эпик>` — префикс эпика, `N` — номер этапа в его плане (нумерация как в
  плане, с 0 или с 1). Набор без эпика — осмысленное имя без префикса.
  Milestones общие на весь репозиторий, имена не должны путаться.
- **Описание.** Этап: `Эпик: #<номер>`; иной набор — цель в одну-две строки.
- **У issue только один milestone** (ограничение GitHub). Поэтому уровни не
  смешиваем: подзадачи эпика — в его этапах, а в сквозной набор (релиз, демо)
  кладём сам эпик или простые задачи, не подзадачи чужих этапов.
- **Ставлю при создании** задачи, если она входит в набор; milestones этапов
  создаю вместе с эпиком, как только план по этапам согласован (поздние этапы
  могут уточняться по итогам ранних).
- **Этап ещё не разбит на задачи** → в milestone лежит одна задача-этап с
  чеклистом (`<Эпик> · Этап N. …`, sub-issue эпика, оценка — на весь этап;
  это исключение из правила «одним PR»). При декомпозиции: сначала создаю
  отдельные issue из пунктов чеклиста (в том же milestone, sub-issues эпика,
  с оценками), затем задачу-этап закрываю как не запланированную и убираю из
  проекта — она не считается ни в `Готово`, ни в оценке эпика (см. «Закрыта
  без выполнения» в разделе про проект).
- **Срок (due date)** — если есть реальный дедлайн, тогда набор виден на
  роадмэпе. Нет дедлайна — не выдумываем.
- **Закрываю сам**, когда закрыта последняя задача набора (как и статусы);
  переоткрываю, если задачу переоткрыли:
  `gh api -X PATCH repos/{owner}/{repo}/milestones/<number> -f state=closed`.

```bash
gh api -X GET repos/{owner}/{repo}/milestones -f state=all           # список
gh api repos/{owner}/{repo}/milestones -f title="Биллинг · 1 · Проектирование" -f description="Эпик: #42"
gh issue edit <N> --milestone "Биллинг · 1 · Проектирование"
```

### Сессия и ветка — одна задача

- **Сессия = задача.** Новую задачу делаем в новой сессии Claude Code (в
  worktree), первый промпт начинается с номера: `#263` или ссылка на issue.
  Планирование эпика (декомпозиция, оценки) — тоже отдельная сессия с
  номером эпика. Правка «на две минуты» в чужой сессии допустима, но её
  время достанется соседней задаче — это осознанная потеря.
- **Ветка = `<type>/<issue>-<slug>`**: `feat/42-invoice-export`,
  `fix/57-login-redirect-loop`, `docs/61-api-guide`,
  `research/73-search-engine-choice`. Один слеш, номер через дефис
  (два слеша дают вложенные refs и папки worktree, а `feat/263` рядом с
  `feat/263/x` git запрещает). `type` — типы conventional commits
  (`feat fix docs refactor perf test chore ci build`) плюс `research`
  (спайк без кода); тот же список — тип задачи в `est`. Slug — латиница,
  kebab-case, 2–5 слов. Если в репозитории принят префикс области
  (`backend/`, `admin/`…), он идёт первым: `backend/fix/263-…`.
- Worktree, созданный из приложения Claude Code, называет ветку сам
  (`claude/<slug>-<hash>`) — это мимо конвенции: ветку заводим руками
  (`git worktree add ../wt-263 -b feat/263-slug`) или переименовываем до PR.
- **PR:** заголовок — conventional commit (`feat(scope): описание`), в теле
  `Closes #263`; squash-коммит наследует заголовок. В репо без PR —
  `Closes #N` в сообщении коммита.

### Оценка и факт — скилл `est`

- **Единица.** «Оценка, ч» и «Факт, ч» — активные часы в Claude Code по
  задаче (работа агента + паузы ≤ 30 мин), не человеко-часы и не календарь.
  Ручную работу вне Claude (> 0,5 ч) человек дописывает в комментарий «Факт»
  строкой «+ вручную: N ч». Старые оценки без маркера `<!-- est -->`
  (поставленные до внедрения `est`, в других единицах) в калибровку не идут.
- **Оценка новой задачи** — только через скилл `est` (`~/.claude/skills/est`):
  скрипт поднимает историю закрытых задач с фактом, агент выбирает 2–3
  аналога и называет поправку, скрипт ставит поле и пишет комментарий
  «Оценка: … Аналоги: …». Аналогов нет — так и пишем: «оценка экспертная,
  доверие C», никакой выдуманной точности.
- **Факт при закрытии** задачи (PR смёржен / issue закрыт) — сразу
  `est fact <N> --write`: комментарий «Факт: …» и поле «Факт, ч». Факт не
  найден — «факт недоступен», не цифра на глаз. Задачи not planned и дубли
  факта не получают. Расхождение вне ×0,5…×2 при оценке ≥ 2 ч — строка
  «Причина: …» в том же комментарии.
- **Привязка работы к задаче** (иначе факта не будет): сессия и ветка по
  разделу выше (номер в первом промпте, ветка `<type>/<issue>-<slug>`,
  `Closes #N` в PR); номер задачи и в задании каждому субагенту / агенту
  workflow; коммитить логическими шагами, не одним коммитом на PR.
- Транскрипты `~/.claude/projects` — источник факта; в
  `~/.claude/settings.json` должно стоять `"cleanupPeriodDays": 365`.

### Как привязать подзадачу к эпику

```bash
# id (не номер!) подзадачи
SUB_ID=$(gh api repos/{owner}/{repo}/issues/<номер-подзадачи> --jq .id)
gh api repos/{owner}/{repo}/issues/<номер-эпика>/sub_issues -X POST -F sub_issue_id=$SUB_ID
```

Список подзадач эпика: `gh api repos/{owner}/{repo}/issues/<номер-эпика>/sub_issues`.
