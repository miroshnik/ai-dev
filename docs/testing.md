# Как тестировать: прогон, окружение, e2e к разделу «Тесты и код»

Правило: какой тест нужен и как он умеет упасть — «Спецификация — решения»
(`skills/spec/canon.md`) и «Тесты и код» в `AGENTS.md`, свой порт и своя
база — `docs/parallel-checkouts.md`.
Здесь — как прогонять, читать итог и писать e2e, которые не флачат. Правила —
для любого стека, примеры — Playwright. От фреймворка зависят три вещи: какие
env-файлы читает каждая команда, что вшивается в сборку и чем поднять
прод-сборку локально, — они в разделе «Фреймворк: три вопроса». Сверено с
документацией Playwright, Next.js, Vite, SvelteKit и Nuxt.

## Прогон и итог

- **Тяжёлый прогон — очередью машины.** Проверки проекта (`lint`,
  `typecheck`, `test`, `test:*`) установка флоу оборачивает в `slot`:
  одновременно идут два прогона, вместе — половина ядер, остальные ждут по
  порядку прихода и печатают, кого ждут (скилл `slot`). Без очереди соседние
  сессии, линтер и e2e другого worktree делят ядра — таймауты и флаки не про
  код. Воркеры раннера — из `AI_DEV_SLOT_CPUS` (четверть ядер), в CI — свои:

  ```ts
  maxWorkers: Number(process.env.AI_DEV_SLOT_CPUS) || undefined,                      // vitest.config.ts
  workers: Number(process.env.AI_DEV_SLOT_CPUS) || (process.env.CI ? 2 : undefined), // playwright.config.ts
  ```

  Время сравнивать по CI или по CPU (`user` у `time`), а не по wall-clock: в
  нём и ожидание очереди. Флаку проверять повтором (`--repeat-each`) —
  скриптом проекта, в слоте, иначе повтор меряет соседей.
- **Долгий прогон — под наблюдением.** Полный прогон, тем более с очередью, —
  не с таймаутом инструмента агента впритык: по таймауту процесс убивают
  посреди тестов (`Killed: 9`), а обёртка (`| tail`, `&& echo ok`, скрипт без
  `set -o pipefail`) может вернуть 0. Фоновой командой с запасом таймаута
  (у Claude Code — до 2 ч, завершение будит сессию) или в терминале;
  ожидание — завершения процесса, а не срока.
- **Итог — по сводке раннера, а не по коду выхода.** Сводка Playwright:
  `passed`, `failed`, `flaky`, `skipped`, `did not run`, `interrupted`; у
  Vitest — строки `Test Files` и `Tests`, у `bun test` — `pass` и `fail`.
  Прогон годен, когда сводка есть, упавших, не запущенных и прерванных нет,
  а флаки разобраны (раздел «Тесты и код»: флака — дефект). Нет сводки —
  прогон не закончился, какой бы ни был код. Фильтр вывода по `Error:` врёт:
  сервер приложения пишет в тот же поток и безвредные ошибки (ожидаемый 404,
  отменённый запрос).
- **Артефакты упавшего теста — сразу в сторону.** Раннер чистит папку
  результатов в начале прогона (у Playwright — `outputDir`, по умолчанию
  `test-results/`): trace, скриншоты и видео — скопировать до повторного
  запуска.

  ```bash
  cp -R test-results "$TMPDIR/e2e-<задача>-$(date +%H%M%S)"
  npx playwright show-trace "$TMPDIR"/e2e-<задача>-*/<тест>/trace.zip
  ```
- **Сборка и прогон по ней — не параллельно.** Каталог сборки (раздел
  «Фреймворк: три вопроса») общий: пересборка под работающим сервером
  подменяет чанки, и открытые страницы падают на их загрузке. Сначала
  сборка, потом прогон; в соседнем терминале того же чекаута — не собирать.

## Окружение

- **Каждая команда читает свои env-файлы, а прод-сервер — иногда никаких.**
  Dev-сервер, сборка и прод-сервер одного приложения берут окружение из
  разных мест (таблица ниже). Env, скачанный с хостинга (`vercel env pull`,
  `netlify env:import` и аналоги), может нести прод-секреты и прод-адреса:
  локальная прод-сборка возьмёт его и пойдёт в прод-базу.
- **Экспорт главнее файлов.** Уже заданную в окружении переменную `.env*` не
  перекрывает (Next.js, Vite и всё, что на нём, dotenv без `override`), а
  прод-сервер, который файлов не читает, видит только экспорт. Локальные
  сборка, прод-сервер и e2e — только с явно экспортированным локальным
  окружением:

  ```bash
  set -a; . ./.env.e2e; set +a        # свой файл, только локальные адреса
  npm run build && npm run test:e2e
  ```
- **Вшитое в сборку экспортом не поменять.** Публичные переменные (и у
  некоторых фреймворков приватные — таблица) подставляются в код при
  сборке: сборка для e2e — с тем же локальным окружением, что и прогон;
  сменил адрес или порт — пересобрать.
- **Куда смотрит env — проверять командой, а не помнить:**

  ```bash
  grep -H -E '^[A-Z_]*_URL=' .env* | sed -E 's#(://[^:]+:)[^@]+@#\1***@#'
  ```

  Гард «ноутбук не подключается к удалённой базе без явного флага» — стандарт
  проекта (`tests/standards/<name>`), а не внимательность.
- **Свежая база на прогон.** CI стартует с пустой базы и ловит гонки
  фикстур; локальная наполненная база их прячет — или наоборот, её старые
  строки всплывают в чужих списках. Прогон — на своей свежей базе
  (`docs/parallel-checkouts.md`). Тест, зелёный на пустой базе CI и
  красный на наполненной локальной, — дефект теста (он зависит от чужих
  данных), а не базы.

## e2e

- **Против прод-сборки, а не dev-сервера.** `webServer.command` — сборка и
  прод-сервер (таблица ниже), а не `dev`. Dev-сервер меняет код под
  прогоном: Next.js компилирует маршрут по первому запросу, Vite (и
  SvelteKit, Nuxt, React Router на нём) на новой зависимости посреди
  прогона пересобирает пакеты и перезагружает страницу — таймауты и
  предупреждения, которых в проде нет.
- **Внешние сервисы — заглушки или эмуляторы** флагами окружения сервера
  e2e (`webServer.env`): почта, платежи, хранилище, LLM. Побочный эффект
  («письмо ушло», «платёж создан») — опросом своей базы или эмулятора, а не
  по UI, который сам зависит от внешнего сервиса.
- **Общие данные — setup-проект, один раз на прогон.** То, что видят все
  параллельные файлы (справочники, каталоги, пользователи для входа),
  создаёт setup-проект раннера, а не `beforeAll` файла: иначе два файла
  одновременно видят «нет — создаю» (TOCTOU) и падают на уникальном ключе
  или делят одну строку.

  ```ts
  // playwright.config.ts
  projects: [
    { name: 'setup', testMatch: /global\.setup\.ts/ },
    { name: 'e2e', dependencies: ['setup'], use: { storageState: 'tests/.auth/user.json' } },
  ],
  ```
- **Своё — под уникальным префиксом.** Данные теста — с префиксом из
  воркера, времени и случайного суффикса
  (`` `e2e-${testInfo.workerIndex}-${Date.now()}-${rnd}` ``); создание и
  чистка — напрямую в базе (фабрики `tests/lib`), а не через UI: UI-шаги
  подготовки медленные и падают не там.
- **Фикстура не всплывает в чужих списках.** Дата создания — в прошлом
  (списки сортируются по ней, новая строка вытеснит ожидаемую первой);
  тест ищет известную сущность по имени, а не первую строку таблицы.
- **Ожидание ответа — до действия и по своему адресу.**

  ```ts
  const saved = page.waitForResponse((r) => r.url().includes(`/api/orders/${id}`) && r.request().method() === 'PATCH');
  await page.getByRole('button', { name: 'Сохранить' }).click();
  expect((await saved).ok()).toBe(true);
  ```

  Зарегистрированное после клика ожидание пропустит быстрый ответ;
  без фильтра по адресу поймает чужой запрос (аналитика, префетч).
- **Первое действие после навигации SSR может потеряться** до гидратации
  (Next.js, Nuxt, SvelteKit, React Router, острова Astro): кнопка уже в
  HTML, обработчика ещё нет. Действие вместе с проверкой результата — в
  повторяемый блок, а не пауза:

  ```ts
  await expect(async () => {
    await page.getByRole('button', { name: 'Фильтр' }).click();
    await expect(page.getByRole('dialog')).toBeVisible({ timeout: 1_000 });
  }).toPass({ timeout: 10_000 });
  ```

  У `toPass` таймаут по умолчанию 0 — повтор до таймаута теста: свой
  `timeout` обязателен. Повторять можно только идемпотентное действие
  (открыть, выбрать), не «создать». У SPA без SSR этой гонки нет: кнопки нет
  до рендера, и раннер её дождётся. Навигация — сразу на канонический URL:
  редирект по пути — лишняя гидратация и гонка. Проверки — web-first
  (`toHaveText`, `toBeVisible`), а не `textContent()` и сравнение снимка.
- **Вход — сохранённой сессией.** Setup-проект входит один раз и пишет
  `storageState`; тесты стартуют с ним, а не заполняют форму входа.
  Визуальная проверка агентом (браузер сессии) — тем же `storageState`, без
  ввода пароля. Форму входа проверяет один тест самого входа.
- **Сторож dev-предупреждения фреймворка** (React, Vue: гидратация, ключи
  списков) — юнитом в dev-режиме (jsdom, happy-dom): прод-сборка
  предупреждения вырезает, в e2e против неё сторож не умеет упасть (раздел
  «Тесты и код»).

## Юниты

- **Мок — на внешнем крае, который ведёт себя как настоящий.** Мок своего
  модуля прячет его поведение (очередь запросов фреймворка, разбор формы,
  транзакцию) и запрещён линтом («Спецификация — решения»,
  `skills/spec/canon.md`). Подменяется
  граница с внешним миром — HTTP чужого API, почта, часы — и так, как она
  отвечает на деле (коды, задержки, формат ошибок по документации).
- **Точка входа — через тот же вход, что в проде.** Обработчик формы —
  `Request` или `FormData` (server action Next.js, `action` React Router,
  form action SvelteKit), маршрут — HTTP-запросом, а не готовым объектом
  прямо в схему валидации: иначе тест не видит разбор формы, приведение
  типов и пропавшие поля.

## Фреймворк: три вопроса

До первого прогона e2e в проекте — ответить по документации его
фреймворка и записать ответ в `docs/` проекта (рецепт окружения):

1. Какие env-файлы читают dev-сервер, сборка и прод-сервер и главнее ли
   уже экспортированное окружение.
2. Что вшивается в сборку и не меняется без пересборки.
3. Чем поднять прод-сборку локально и где её каталог.

| Фреймворк | Кто читает `.env*` | Вшивается при сборке | Прод-сборка локально | Каталог |
|---|---|---|---|---|
| Next.js | `dev` — `.env.development*`, `build` и `start` — `.env.production*`, `.env.local` и `.env` — оба; в `NODE_ENV=test` `.env.local` не читается | `NEXT_PUBLIC_*` | `next build && next start` | `.next` |
| Vite (SPA) | `dev` — `.env.development*`, `build` — `.env.production*` (`--mode` меняет), `.env[.local]` — оба; прод — статика, окружения нет | `VITE_*` (`import.meta.env`) | `vite build && vite preview` — только для проверки, не прод-сервер | `dist` |
| SvelteKit (adapter-node) | `dev` и сборка — как Vite; `node build` `.env` не читает — `node --env-file=<файл> build` | весь `$env/static/*`, и приватный; `$env/dynamic/*` — в рантайме | `vite build && node --env-file=.env.e2e build` | `.svelte-kit`, `build` |
| Nuxt | `dev`, `build`, `generate`, `preview` — `.env` (другой файл — `--dotenv`); `node .output/server/index.mjs` — не читает | `runtimeConfig`, заданный через `process.env.<другое имя>`; в рантайме его переопределяют только `NUXT_*` | `nuxt build && nuxt preview` (читает `.env`) | `.nuxt`, `.output` |

Фреймворка нет в таблице (React Router, Astro, бэкенд без фронта) — те же
три вопроса к его документации; ответ — в `docs/` проекта, а не в память.

## Знание о тестах в проекте

- `docs/` проекта — только рецепты своего окружения: какие env-файлы,
  контейнеры, эмуляторы, хостинг, как их поднять, ответы на три вопроса
  выше.
- Проверяемое правило о тестах («e2e не мокают свой API», «фикстуры — с
  префиксом») — стандарт `tests/standards/<name>`, а не абзац в документе.
- Знание о хелпере (что создаёт фабрика, что чистит, какие права у
  пользователя) — в его JSDoc в `tests/lib`: подсказка редактора его
  покажет, документ — нет.
- Урок, повторившийся в двух проектах, — задача в ai-dev на этот справочник
  (раздел «Этот файл и скиллы»), а не память агента.
