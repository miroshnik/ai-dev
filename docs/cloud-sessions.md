# Облачная сессия Claude Code

Справочник к строке про облачную сессию в `AGENTS.md`. Облачная сессия —
Claude Code на claude.ai/code, в том числе запущенный из приложения на
телефоне: временный контейнер, в который склонирован только репозиторий
проекта.

## Что она видит

Только репозиторий проекта. Правил и скиллов с машины пользователя
(`~/.claude/rules`, `~/.claude/skills`) и памяти агента там нет. Канон и
скиллы у облачной сессии есть, только если флоу установлен в проект:
`npx -y github:miroshnik/ai-dev install` кладёт копию в `.agents/`, а
симлинки в `.claude/rules` и `.claude/skills` приходят вместе с клоном (README
ai-dev, «Установка»). Версия — та, что закоммичена; обновление —
переустановка и PR.

Проверка: в облачной сессии проекта попросить агента процитировать правило
из `AGENTS.md` и перечислить скиллы — `est`, `spec`, `ci-wait` должны быть.

## Чего в облаке нет (проверено 2026-09-25)

- **GraphQL GitHub** закрыт прокси сессии («use the REST API»). REST — только
  пути `repos/{owner}/{repo}/…` репозиториев сессии; **Projects v2**
  (`users/…/projectsV2…`, `orgs/…`) — 403. Поля проекта (`Status`,
  «Оценка, ч», «Факт, ч», токены, стоимость) из облака не поставить; `est`
  не считает ни оценку, ни факт.
- **Запись в репозиторий** (push, правка issue, комментарии, PR) — только
  если у Claude GitHub App есть доступ к репозиторию. Нет доступа — 403
  («Resource not accessible by integration», «Claude doesn't have GitHub
  access»): пользователь ставит или переподключает приложение
  (claude.ai → Settings → Connectors → GitHub; github.com/apps/claude).
- **Ветку назначает облако** (`claude/<slug>`) и запрещает пушить в другие
  без явного разрешения. Ветку по конвенции `<type>/<N>-<slug>` заводить —
  спросив пользователя в начале, вместе с вопросами по задаче.
- **Название сессии** (`set_session_title`) хранится на сервере и в
  транскрипт не попадает: `est` привязывает облачную работу к задаче только
  по ветке, `#N` в первом промпте и хешам коммитов.
- **Контейнер временный**: незапушенное пропадёт.

## Закрытие задачи из облака

1. `est fact <N>` печатает комментарий «Факт недоступен (облако)» со ссылкой
   на сессию и маркером `<!-- fact {…, "src": "cloud"} -->` — записать его в
   issue инструментом GitHub. Транскрипт облачной сессии остаётся в облаке;
   цифру факта даёт локальная сессия: импортирует события облачной сессии
   браузером (скилл `est`, раздел «Облачная сессия») и пишет
   `est fact <N> --write`. Коммиты облачной сессии несут трейлер
   `Claude-Session` — по нему `est` видит, что часть работы ещё не
   импортирована (покрытие `partial`).
2. `Status` = «Готово» ставит встроенный workflow проекта «Item closed»
   (включён ли — проверяет локальная сессия скиллом `github`); не включён —
   попросить пользователя поставить статус.
3. Актуализация блока — как обычно (issues, sub-issues, milestones доступны
   через REST репозитория); чего не сделать из облака (поля проекта, оценки
   новых задач через `est`) — в комментарий «Состояние» для локальной сессии.

## Push не прошёл — доводит локальная сессия

Облачная сессия, которой запись закрыта, отдаёт работу файлами: ветку —
`git bundle` или `git format-patch --stdout` (вложение сессии), ответы на
вопросы — в тексте PR или итогового сообщения. Локальная сессия по номеру
задачи:

1. Ответы из облака — в «## Вопросы» задачи (✅ и ответ), до кода.
2. Ветку — от свежего `origin/main`: `git fetch <файл>.bundle <ветка>:<ветка>`
   или `git am <файл>.mbox`; если облако начинало не с него — rebase.
3. Ревью диффа и те же проверки, что в CI, **на этой машине**: облако — Linux,
   и платформенные различия (симлинки через `/var` → `/private/var` на macOS)
   там не видны.
4. Дальше как обычно: PR, зелёные чеки, мерж, факт. Факт увидит только
   локальную часть работы — строка «Причина: пропущена работа: …» со ссылкой
   на облачную сессию.
