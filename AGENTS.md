# Общие правила для всех проектов

## Этот файл и скиллы

Канон правил для любого агента: Claude Code, Codex, Gemini CLI, Cursor,
Copilot, OpenCode, Amp читают `AGENTS.md` сами или по ссылке из своего
файла. Живёт в репозитории **miroshnik/ai-dev** (`~/Projects/ai-dev`) вместе
со скиллами (`skills/*`) и справочниками (`docs/`; пути `docs/…` в правилах —
рядом с этим файлом). Установка — `npx -y github:miroshnik/ai-dev install`:
правила, справочники и все скиллы копией в `.agents/` проекта (коммитится —
облачная сессия и CI видят ровно эту версию), с `-g` — на машину, всем
агентам, которые на ней есть, с `-g --link` из клона — симлинками. В
`AGENTS.md` проекта — только ссылка на `.agents/ai-dev/AGENTS.md`: целиком
он не влезет в бюджет Codex `project_doc_max_bytes` (32 КиБ). Здесь — только
общее для всех проектов; частное для проекта — в его спеке `tests/` (раздел «Знание
проекта и передача работы»). Правка правила
или скилла по ходу чужой сессии — отдельный коммит с
осмысленным сообщением и пуш в `main` из главного чекаута, без отдельной
просьбы; задача ai-dev — по общим правилам: ветка, PR, зелёные чеки. Задачи
по правилам и скиллам — в issues ai-dev, проект `ai-dev` (№6).

**Облачная сессия** Claude Code (claude.ai/code) видит только репозиторий:
канон и скиллы у неё есть, только если флоу установлен в проект. Проекты
GitHub ей недоступны: при закрытии задачи — комментарий «Факт недоступен
(облако)» (текст печатает `est fact <N>`), «Готово» — workflow проекта или
пользователь, остальное — в «Состояние»; не смогла запушить — ветку
доводит локальная сессия (`docs/cloud-sessions.md`).

**Репозиторий публичный.** В нём — только общие правила и скиллы. Никаких
названий, владельцев, путей и номеров проектов других репозиториев, имён
коллег и заказчиков — ни в файлах, ни в истории git, ни в issues и
комментариях ai-dev. Примеры в правилах — вымышленные. Личная конфигурация
(какие репозитории есть, где лежат, номера проектов) живёт только в
локальной конфигурации (реестр скилла `est`), не в этом репозитории.

**Скилл = промпт + скрипты** по открытому стандарту Agent Skills
(agentskills.io): папка `<name>/` с `SKILL.md` (frontmatter `name` = имя
папки, `description`; тело < 500 строк) и `scripts/` для детерминированной
части; при необходимости `reference.md`. Скрипты — TypeScript под Bun
(`bun script.ts`: без сборки, без зависимостей, импорт с `.ts`); тесты
скриптов — `bun test` в `tests/` ai-dev по тому же дереву. Исключение —
установщик `bin/ai-dev.mjs`: JavaScript, потому что npx запускает его из
`node_modules`, где Node типы не стирает. Всё, что зависит от конкретных
репозиториев, — в локальную конфигурацию, не в скилл.

Правила читают и автономные рутины. Правка действует там, где правила стоят
симлинком на клон, — с `git pull` клона; в копии (проект, машина) — с
`update` (раздел ниже).

## Первый шаг сессии — актуальный флоу

Правила грузятся в контекст на старте сессии: на отставшем флоу сессия
работает по старым правилам. Поэтому первым делом, до задачи, —
`npx -y github:miroshnik/ai-dev check -g` (машина) и `check` (проект); в
Claude Code их запускает хук `SessionStart`, вывод — в начале контекста.
Код 0 — актуально, 1 — отстаёт, 2 — проверка недоступна.

- **Отстаёт** — `update` (`-g` — машина): клон `--link` — `git pull
  --ff-only`, копия — переустановка. Копию в проекте — отдельным коммитом
  `chore(agents): флоу ai-dev <sha>` в ветку текущей задачи, без отдельного
  спроса; ветки задачи нет — не коммитить, сказать. Затем перечитать
  обновлённое (`AGENTS.md`, `claude/CLAUDE.md`, затронутые скиллы) и
  следовать ему, а не загруженному на старте.
- **`update` отказал** (клон не на `main`, изменения в отслеживаемых файлах)
  или **проверка недоступна** (нет сети, npx) — клон за пользователя не
  чинить, работать по текущему флоу и сказать об этом.
- **Облачная сессия** не обновляет — работает по копии в проекте.

## Язык

Общение, issues (заголовки, описания, комментарии, чек-листы), документы и
планы — по-русски и коротко. Код, идентификаторы, термины, тип и
scope conventional commit — по-английски; описание коммита и PR — по-русски.

## Что делаю без спроса, а что — по разрешению

- **Без спроса:** чтение и поиск, тесты, lint, typecheck, build, локальные
  правки файлов (в своём чекауте), подъём локальной инфраструктуры (Docker,
  dev-база), чтение логов и read-only запросы к внешним системам; ведение задач по разделу «Ведение задач» (issues, комментарии
  «Оценка», «Факт», «Состояние», «Вопросы», поля проекта, milestones,
  лейблы); перезапуск своего прогона CI, закрытие своего дубль-PR, удаление
  своего влитого после мержа (ветка, worktree — раздел «Git, PR и мерж»);
  обновление флоу и коммит его копии (раздел «Первый шаг сессии»).
- **Только по явному «да»** — всё необратимое или внешнее: `git commit`,
  `git push`, мерж, деплой, тег, миграции и записи в живые базы, настройки
  внешних сервисов, удаление чужих или невлитых удалённых веток и данных,
  исходящие сообщения.
- **Разрешение — на конкретное действие и на этот раз.** «Закоммить» ≠ «и
  запушь», «правь что нужно» ≠ согласие на мерж; прошлое «да» не
  переносится. Одно «закоммить» покрывает всю текущую работу логическими
  шагами. Репозиторий может задать иной режим в своём `AGENTS.md`. «Делай
  полностью сам» снимает промежуточные подтверждения на названную задачу;
  стоп только при расхождении, меняющем объём или подход. У автономной
  рутины разрешение — её задание: делает ровно то, что названо (коммит, PR);
  мерж, деплой, внешние настройки — только если названы явно.
- **Секреты и обходы защиты — только с разрешения:** токены, ключи,
  bypass-секреты, отключение проверок у хостинга, CI или облака — сначала
  называю, что появится и где. Секрет из чата нигде не сохраняю (память,
  файлы, коммиты, issues, логи); по завершении напоминаю ротировать.

## Ведение задач

- Задачи ведём в **GitHub Issues** репозитория проекта (скилл `github`:
  `task new`, `task status`, `task drop`), а не в локальных списках,
  TODO-файлах или встроенном списке задач агента.
- **У каждого issue есть тип** (Issue type организации, не метка) — ровно
  три: **«Задача»** (по умолчанию: единица работы на один PR), **«Баг»**
  (дефект: то, что уже есть, работает не так), **«Эпик»** (большая задача с
  подзадачами). Других типов нет: Task/Bug переименованы, Feature выключен.
  Тип ставится при создании (`github task new --type`), типы организации
  настраивает `github project fix`. В репозиториях личного
  аккаунта типов нет — там эпик помечаем меткой `epic`, это единственное
  исключение.
- **Метки решений** `type:name` — `capability:<name>`, `standard:<name>`,
  `architecture:<name>` (папка `tests/…/<name>` или модуль модели): у задачи
  с кодом — метка каждого решения, которое она вводит или меняет
  (`github task new --labels`, по диффу PR — `github pr labels <PR>`); без
  меток — только задача без кода. У эпика — объединение меток подзадач. Цвет —
  по виду, набор сверяет с деревом спеки основной ветки `github project check`.
- **Маленькая задача** — один issue типа «Задача» или «Баг».
- **Большая задача** — эпик + подзадачи:
  - эпик — issue типа «Эпик»: цель, контекст, план (по этапам, если они
    есть), критерии готовности;
  - у эпика есть **короткий префикс** (`Биллинг`, `Импорт`, `API`): с него
    начинаются заголовки эпика и всех его подзадач (`<Префикс> · <заголовок>`),
    он же идёт в названия milestones;
  - каждая подзадача — отдельный issue, привязанный к эпику как **sub-issue**
    (нативные sub-issues GitHub; `github task new --epic N`);
  - подзадача должна быть законченной единицей работы, которую можно сделать
    одним PR;
  - эпик может разбить план на этапы — тогда этап это milestone (раздел
    ниже) и каждая подзадача принадлежит одному этапу; эпик без этапов —
    без milestones.
- **Зависимости — только встроенными связями GitHub** (Relationships), не
  текстом в описании: родитель — sub-issue (эпик), «блокируется» —
  *blocked by*, «блокирует» — *blocking*; при создании —
  `github task new --blocked-by`.
  Разделов «Зависит от» / «После #N» не пишем; зависимость не issue (ответ
  заказчика, внешний срок) — заводим под неё задачу или пишем в «Контекст».
  *Relates to* — только в UI и только если связь не «блокирует». Задача с
  непустым *blocked by* не берётся в работу, пока блокеры не закрыты.
- Перед созданием новой задачи проверяем, нет ли уже такой
  (`gh issue list --search`); перед началом работы — не идёт ли она уже в
  параллельной сессии (раздел «Git, PR и мерж»).
- Статус ведём только в поле `Status` проекта (раздел ниже), в самом issue
  ничего не дублируем; PR связываем с задачей (`Closes #N`); эпик закрываем,
  когда закрыты все подзадачи.
- Нет GitHub-репозитория — сказать и спросить, где вести задачи, а не
  заводить их молча в другом месте.

### Проект (GitHub Projects)

У каждого репозитория есть **ровно один** GitHub Project, привязанный к репо
(`github project fix`); название проекта = имя репозитория. В нём **все** эпики и
задачи репозитория — отдельных проектов под эпик/направление не заводим
(направление = эпик внутри общего проекта). Все задачи добавляются в
проект сразу при создании (`github task new`). Обязательно:

- **Три представления**, ровно с такими именами: `Доска` (BOARD_LAYOUT,
  колонки по `Status`), `Таблица` (TABLE_LAYOUT), `Роадмэп` (ROADMAP_LAYOUT).
- **Поле `Status`** с вариантами: `Бэклог` → `В работе` → `Готово`.
  Статус меняю **сам, сразу**, не дожидаясь просьбы
  (`github task status <N> <статус>`):
  - новая задача — при создании ставлю `Бэклог`;
  - взял задачу в работу — до начала работы ставлю `В работе`;
  - закончил (PR смёржен / задача закрыта) — ставлю `Готово`;
  - задачу переоткрыли (баг вернулся, PR откатили) — возвращаю `В работе`
    (или `Бэклог`, если работа не ведётся); уже закрытые milestone и эпик
    при этом переоткрываю;
  - **закрыта без выполнения** (не будем делать, дубль, заменена другими
    задачами) — закрываю как not planned и **убираю из проекта**
    (`github task drop <N>`): в `Готово` она не попадает, в оценке эпика не
    считается.
  Эпик: `В работе`, когда взята первая подзадача; `Готово`, когда готовы все
  (закрытые как not planned не в счёт — их в проекте уже нет).
  Страховка — встроенные workflow проекта «Item added to project» →
  `Бэклог`, «Item closed» → `Готово` и «Auto-add to project» (новые
  открытые issues репозитория сами попадают в проект): статус встанет, даже
  если ставить его некому (облачная сессия, другой агент, закрытие из UI
  GitHub). Агент статус ставит всё равно; закрытую как not planned убирает
  из проекта — иначе workflow запишет её в `Готово`.
- **Поле `Оценка, ч`** (Number) — активные часы агента (раздел «Оценка и
  факт»). Ставится **только через скилл `est`** — по аналогам с фактом, не из
  головы: у каждой подзадачи и маленькой задачи при создании; у эпика —
  сумма оценок подзадач, пересчитываю при добавлении подзадачи или изменении
  её оценки. После начала работы оценку не переписываю — расхождение
  объясняется в комментарии «Факт».
- **Поля `Факт, ч`, `Токены, млн`, `Стоимость, $`** (Number) — факт: активные
  часы, все токены привязанных ответов модели (вход, выход, запись и чтение
  кэша, включая субагентов) и их цена по публичным API-тарифам —
  **API-эквивалент**, на подписке не списывается, но сравним между задачами
  и моделями. Заполняет только `est fact --write` при закрытии задачи, руками
  не трогать; у эпика — сумма подзадач.
- **Приоритет — встроенное поле issue `Priority`** (Issue field организации,
  есть у неё по умолчанию: `Urgent` → `High` → `Medium` → `Low`), а **не**
  своё поле проекта.
  Обязателен у каждой открытой задачи: новой ставлю `Medium`, если
  пользователь не сказал иначе; у эпика — не ниже самой срочной открытой
  подзадачи. Поле подключено в проект, `Таблица` и `Доска` **сортируются по
  нему**; внутри приоритета порядок ручной. Берём в работу самое
  срочное из незаблокированного. В личном аккаунте полей issue нет —
  приоритет не ведём. Ставит `github task new` (`--priority`, по умолчанию
  `Medium`).

Ничего лишнего: других полей (Iteration, Готовность…) и представлений нет,
пока их не внесли сюда. Готовность — статус и *blocked by*, этапы —
milestones (поле `Milestone`).

Проект — скилл `github`: `project check` раз в сессию перед работой с
задачами, ❌ — `project fix`. Проекта нет — `fix` привяжет, скопирует эталон
или создаст; чего нет в API (workflow, сортировка) — шаги UI: агент проходит
их браузером сессии без отдельного спроса, без браузера — ссылки
пользователю. Удалять или переименовывать в проекте, которым уже
пользовались, и менять настройки организации — только после подтверждения
(`fix --confirm`).

### Milestones — наборы задач

Milestone (встроенная сущность репозитория) — **просто именованный набор
задач** с общей целью и, если есть, сроком; ничего другого для группировки
(спринты, своё поле «Этап»/«Фаза»/«Релиз») не используем. Состав решает
смысл: простые задачи (`Релиз 2026-10`), эпики целиком (milestone у самих
эпиков), **этап эпика** (набор его подзадач).

- **Не обязателен** ни задаче, ни эпику: заводим, только когда группу надо
  отслеживать как целое. Эпик без плана по этапам — без milestones.
- **Название** этапа: `<Эпик> · <N> · <Название этапа>`
  (`Биллинг · 1 · Модель данных`), `N` — номер этапа в плане (с 0 или с 1);
  набор без эпика — осмысленное имя без префикса; имена не должны путаться. **Описание** этапа: `Эпик: #<номер>`;
  иного набора — цель в одну-две строки.
- **У issue только один milestone**, поэтому уровни не смешиваем: подзадачи —
  в этапах своего эпика, в сквозной набор (релиз, демо) кладём сам эпик или
  простые задачи.
- **Ставлю при создании** задачи, если она входит в набор; milestones
  этапов создаю вместе с эпиком,
  как только план согласован (поздние этапы могут уточняться).
- **Этап ещё не разбит** → в milestone одна задача-этап с чеклистом
  (`<Эпик> · Этап N. …`, sub-issue эпика, оценка на весь этап; исключение из
  правила «одним PR»). Декомпозиция: issue из пунктов чеклиста (тот же
  milestone, sub-issues, с оценками), затем задача-этап — not planned и из
  проекта.
- **Срок** — только реальный дедлайн (тогда набор виден на роадмэпе).
- **Закрываю сам**, когда закрыта последняя задача набора; переоткрываю,
  если задачу переоткрыли. При создании задачи — `github task new --milestone`,
  остальные команды — скилл `github`.

### Сессия и ветка — одна задача

- **Сессия = задача.** Новую задачу делаем в новой сессии агента (в
  worktree), первый промпт начинается с номера: `#263` или ссылка на issue.
  Планирование эпика (декомпозиция, оценки) — тоже отдельная сессия с
  номером эпика.
- **Сессия называется `#<номер> <название задачи>`** — ровно заголовок issue
  с номером впереди: `#42 Биллинг · Экспорт счетов в PDF`. Переименовываю
  сессию сам, как только понятно, какую задачу делаем (инструментом
  переименования сессии; если его нет — прошу пользователя). Так сессию
  видно в списке, а `est` по названию привязывает её к задаче надёжнее, чем
  по тексту первого промпта. Сессия без задачи (вопрос, обсуждение правил)
  называется по смыслу, без номера. Правка «на две минуты» в чужой сессии
  допустима, но её время достанется соседней задаче — это осознанная потеря.
- **Ветка = `<type>/<issue>-<slug>`**: `feat/42-invoice-export`,
  `fix/57-login-redirect-loop`, `docs/61-api-guide`,
  `research/73-search-engine-choice`. Один слеш, номер через дефис
  (два слеша дают вложенные refs и папки worktree, а `feat/263` рядом с
  `feat/263/x` git запрещает). `type` — типы conventional commits
  (`feat fix docs refactor perf test chore ci build`) плюс `research`
  (спайк без кода); тот же список — тип задачи в `est`. Slug — латиница,
  kebab-case, 2–5 слов. Если в репозитории принят префикс области
  (`backend/`, `admin/`…), он идёт первым: `backend/fix/263-…`.
- Worktree, созданный инструментом агента, может назвать ветку сам — это
  мимо конвенции: ветку заводим руками (команда — раздел «Git, PR и мерж»)
  или переименовываем до первого push (`git branch -m`).
- **PR:** заголовок — conventional commit (`feat(scope): описание`), в теле
  `Closes #263`. Способ мержа (squash / merge / rebase) задаёт репозиторий —
  в своём `AGENTS.md` или настройках
  (`gh repo view --json squashMergeAllowed,rebaseMergeAllowed,mergeCommitAllowed`).
  При squash заголовок PR становится заголовком коммита (у PR из одного
  коммита с настройкой по умолчанию — сообщение этого коммита); при rebase и
  merge в `main` уходят сами коммиты — поэтому conventional commit и у
  заголовка PR, и у каждого коммита. В репо без PR — `Closes #N` в сообщении коммита.

### Открытые вопросы — в начале работы

Вопросы по задаче живут в её описании, в разделе «## Вопросы» (нумерованный
список; пока есть неотвеченные — на задаче лейбл «вопросы»). Беря задачу в
работу, **первым делом** — до плана, кода и субагентов — читаю «## Вопросы»
задачи и эпика и **задаю все открытые (без ✅) пользователю** одним
сообщением, с вариантами и своей рекомендацией по каждому. Не откладываю:
ответ может поменять объём и подход, а в начале сессии пользователь рядом.

- Сначала отсеиваю то, на что ответ уже есть (комментарии, соседние задачи,
  код): помечаю ✅ с ответом и не задаю.
- Свои вопросы по задаче и коду задаю тем же сообщением и дописываю в
  «## Вопросы», продолжая нумерацию.
- Пока жду ответа, делаю то, что от него не зависит; зависящее не начинаю и
  ответ допущением не подменяю.
- Ответ получен — сразу в issue: ✅ и ответ у вопроса, нумерация не меняется;
  открытых не осталось — снимаю лейбл «вопросы».
- Автономная рутина (спросить некого): задачу с блокирующими открытыми
  вопросами не беру — они ждут ответа в issue.

### Оценка и факт — скилл `est`

- **Единица.** «Оценка, ч» и «Факт, ч» — активные часы агента по задаче
  (работа агента + паузы ≤ 30 мин), не человеко-часы и не календарь. Ручную
  работу вне агента (> 0,5 ч) человек дописывает в комментарий «Факт»
  строкой «+ вручную: N ч». Старые оценки без маркера `<!-- est -->`
  (в других единицах) в калибровку не идут.
- **Оценка новой задачи** — только через скилл `est`: скрипт поднимает
  историю закрытых задач с фактом, агент выбирает 2–3 аналога и называет
  поправку, скрипт ставит поле и пишет комментарий «Оценка: … Аналоги: …».
  Аналогов нет — так и пишем: «оценка экспертная, доверие C», никакой
  выдуманной точности.
- **Факт при закрытии** задачи (PR смёржен / issue закрыт) — сразу
  `est fact <N> --write`: комментарий «Факт: …» (часы, токены по видам,
  стоимость по моделям) и поля «Факт, ч», «Токены, млн», «Стоимость, $». Факт
  не найден — «факт недоступен», не цифра на глаз. Задачи not planned и дубли
  факта не получают. Расхождение вне ×0,5…×2 при оценке ≥ 2 ч — строка
  «Причина: …» в том же комментарии.
- **Привязка работы к задаче** (иначе факта не будет): сессия и ветка по
  разделу выше (номер в первом промпте, ветка `<type>/<issue>-<slug>`,
  `Closes #N` в PR); номер задачи и в задании каждому субагенту / шагу
  автоматизированного workflow; коммиты — по разделу «Git, PR и мерж».
- Источник факта — транскрипты агента. Сейчас `est` читает только
  транскрипты Claude Code (`claude/CLAUDE.md`); у задачи, сделанной другим
  агентом, факт «недоступен», пока не добавлен его источник (Codex — #12).

### Актуализация блока при закрытии задачи

Задача закрыта (PR смёржен / issue закрыт) — сразу после факта прохожу по
**всем открытым задачам того же эпика/блока** и привожу их в соответствие с
выкаченным. Это часть закрытия задачи, а не отдельная просьба. Пять
проверок:

1. **Сделанное — закрыто.** Нет открытых задач, уже вошедших в выкаченное
   (сделана — закрываю, потеряла смысл — not planned и убрать из проекта).
   Статусы и milestones соответствуют: закрыта последняя задача набора —
   закрываю milestone.
2. **Отвеченные вопросы — помечены.** Каждый уже отвеченный вопрос в
   «## Вопросы» (комментарии, другая задача, код) помечен ✅ с ответом;
   нумерация не меняется — на неё ссылаются. Открытых нет — снимаю лейбл
   «вопросы».
3. **Описания — не врут.** Формулировки открытых задач сверены с кодом и
   спеками: убрано то, чего после выкатки не существует (поля, таблицы,
   маршруты, права). После **отмены принятого решения** правлю все задачи,
   где оно процитировано.
4. **Зависимости — реальные.** Связи GitHub (sub-issue, blocked by) отражают
   положение дел: снят blocked by на закрытые задачи, новая задача привязана
   к эпику, пометки «⛔» в тексте совпадают со связями.
5. **Повторы — стандарт.** Решение, которое в выкаченном повторяет уже
   существующее в двух и более местах, — issue «Стандарт · …» (правило в
   `tests/standards/` и рефакторинг); отложенное «не в этом PR» — issue или
   снято явно, а не забыто.

Что поправил — одной строкой в комментарии к эпику: история решений в одном
месте.

## Git, PR и мерж

- **Беря задачу в работу** — не идёт ли она уже в параллельной сессии:
  `gh pr list --state open --search "<N>"` и
  `git fetch --prune && git branch -a --list "*/<N>-*"` (и незапушенные ветки
  соседних worktree). Идёт — продолжаю ту работу или жду мержа; два PR
  на одно и то же — второй закрываю (`gh pr close`), не мержу оба.
- **Ветка — только от свежего `origin/main`:**
  `git fetch origin && git worktree add --no-track ../wt-263 -b feat/263-slug origin/main`,
  первый push — `git push -u origin HEAD`. Локальный `main` и любой снимок
  истории или статуса, показанный агенту при старте сессии, устарели. В
  `main` — только через PR; прямой push в `main` — только по прямому
  указанию владельца.
- **Коммичу логическими шагами** (один шаг — один коммит, сообщение по
  conventional commits), не одним коммитом на PR.
- **Подъехал чужой PR** — сразу `git fetch && git rebase origin/main`, не
  дожидаясь конфликта; push после rebase — `git push --force-with-lease` (не
  `--force`), с разрешением как обычно.
- **Сразу после мержа PR — влитое удаляю целиком, без спроса:** чекаут
  сессии с влитой ветки долой —
  `git fetch --prune && git switch --detach origin/main && git branch -D <ветка>`,
  удалённую ветку — `git push origin --delete <ветка>`, если хостинг не
  удалил сам, свои worktree и временные ресурсы сессии (базы, контейнеры).
  «Влито» — по PR (`gh pr view <N> --json state` = `MERGED`) или
  `git cherry origin/main <ветка>`, не `git branch --merged`: после squash
  или rebase git не видит, что ветка влита, — панель сессии и `git status`
  зовут на второй PR, push в ней воскресит удалённую. Чужие ветки и worktree
  живых сессий не трогаю, невлитое — никогда. Следующая задача — новая ветка
  от `origin/main`.
- **Перед push** — `git branch --show-current` (своя ветка, а не локальный
  `main`: после серии checkout и rebase push уходил мимо PR), `git fetch` и
  `git rev-list --count HEAD..origin/main`;
  не 0 — rebase и повторная проверка того, что зависит от общего состояния
  (нумерация миграций и решений, общие списки).
- **Полный SHA — только из git:** `git fetch origin && SHA=$(git rev-parse origin/main)`
  или `git log -1 --format=%H`; короткий не достраиваю, «похожий» из памяти
  не беру: по несуществующему SHA API молча отдаёт пустой статус.
- **Мерж — только при всех зелёных чеках**, включая превью-деплой;
  «известный красный первый билд» — не исключение: перезапускаю свой упавший
  прогон (`gh run rerun <id> --failed`) и жду зелёного, красный по другой
  причине — чиню до мержа. Жду циклом опроса: по номеру PR —
  `gh pr checks <N>`, по полному SHA из git — API (механика и ловушки —
  `docs/pr-checks.md`; скилл `ci-wait`). Пустой список или
  `no checks reported` — «ещё не зарегистрированы», а не «прошли».
- **Мерж, который выкатывает** (деплой из `main`), — ещё не конец задачи: до
  доклада «готово» жду статусы на SHA мержа — деплой и проверки после него
  (скилл `ci-wait`, `status <sha> --context <имя>`). Смоук прода — проверка
  в CI проекта, а не ручной шаг агента. Упал — логи и починка сразу: это
  блокер доклада и закрытия задачи.
- **Перед коммитом — ровно те проверки, что гоняет CI**, репозиторными
  скриптами (`lint`, `typecheck`, `test` из `package.json` / Makefile — те
  же, что вызывает CI), а не своими вариантами команд; перед мержем — полная
  сборка. В цепочках `script | tail` статус берётся от последней команды:
  `set -o pipefail` или не пайпить.
- `gh pr merge --delete-branch` из worktree локальную ветку не удаляет
  (старый gh падает с `'main' is already used by worktree`) — это не ошибка
  мержа: проверяю `gh pr view <N> --json state`, merge не повторяю.

## Спецификация — решения

Спека проекта — **решения с механической проверкой**: что система делает, из
чего состоит, каким правилам подчиняется код. Проверка — как система должна
работать, код — как она работает: какой код, так система и работает, поэтому
источником должного код быть не может. Отдельных спецификаций нет: решение
существует, только пока его проверяет механизм — тест, линт-правило,
проверка над моделью архитектуры. **Нет проверки — нет решения, нет решения —
нет кода:** поведение без проверки можно менять без согласования, а убрать
то, чем пользуются, — только решением в issue; стандарт без проверки не
действует; код, которого не заявляет ни одно решение, — мёртвый и удаляется.

- **Решение — единица спеки, папка — его дом.** Анатомия одна для всех
  видов:
  - `<папка>.md` — зачем и для кого, причина и отвергнутые альтернативы;
    первый абзац — описание в оглавлении; метка `<!-- spec: … -->` ставит в
    рассказ генерируемую схему (C4, сиквенс). JSDoc-шапок у файлов тестов нет;
  - главный файл `<папка>.test.ts` — утверждения: разделы страницы идут в
    порядке его `describe`, главное — первым; рядом — остальные `*.test.ts`,
    `*.e2e.ts`;
  - механизм — в той же папке: фрагмент `eslint.ts`, `rule.yml` ast-grep.
    Конфиги инструментов проекта (`eslint.config.*`, `sgconfig.yml`) только
    собирают их из дерева (`collectEslint` скилла `spec`) — у правила один
    дом;
  - `exceptions.ts` — исключения (ниже).
- **Три корня `tests/` — по вопросу читателя,** вид инструмента в структуре
  не кодируется:
  ```
  tests/
    capabilities/<name>/   что система делает: поведение — юнит, интеграция, e2e
    architecture/          из чего состоит: model.ts — C1 внешние системы (адаптер,
                           хосты, ключи окружения), C2 контейнеры (связи, конфиги
                           деплоя), C3 модули (каталог, назначение, API, от кого
                           зависит, пакеты); <name>/ — проверки над моделью
    standards/<name>/      каким правилам подчиняется весь код: соглашения формы
                           и сквозные инварианты
    lib/                   фабрики, база, helpers — не спека, в доку не попадает
  ```
  Плоско, без подсистем; имя папки — идентификатор решения на английском.
  **Один факт — один дом:** общее правило («каждая мутация пишет аудит») — в
  `standards/`, поведение самого журнала — в своей capability, в остальных
  capability о нём ни слова.
- **Механизм — по тому, что фиксируем** (как подключить — `checks.md` скилла
  `spec`); каждый обёрнут тестом раннера, поэтому `spec-doc` и `spec-diff`
  видят всё одним путём:
  - поведение — тест: алгоритм — юнит, подсистема — интеграционный,
    взаимодействие подсистем — e2e; уровень в имени не кодируется, суффикс
    `.e2e.ts` нужен только раннеру;
  - соглашение формы («нет `console` в домене») — линт-правило с примерами
    (`examples` харнесса): «нельзя» даёт ошибку правила, «можно» и файл вне
    охвата — нет;
  - поведенческое соглашение — «реестр + инвариант» (`invariant`): реестр из
    кода (роутер, схема, файлы), тест на каждый элемент, тест «реестр не
    пуст» и нарушитель, на котором проверка падает;
  - границы и зависимости — модель архитектуры: `boundariesConfig` (ESLint,
    ошибка видна в редакторе) и `architecture` (каталог — в модуле, пакет
    разрешён модулю и используется, внешняя система — только через адаптер,
    модуль — в одном контейнере); граф целиком (циклы, сироты) —
    dependency-cruiser, только когда он нужен;
  - порядок взаимодействия, когда он сам решение («сначала резерв, потом
    списание»), — `sequence` с `order` по трассе `trace` на границах модели.
- **Проверка умеет упасть и не флачит** (раздел «Тесты и код»): тест
  пишется до кода и сначала красный, линт-правило доказывает «нельзя»
  примером, инвариант — нарушителем, исключение — храповиком. `.only`,
  `skip` без причины и номера issue, ретраи, моки своих модулей (подменять
  можно только внешние края) — ошибка линта.
- **Заявленность — код держится за решения в точках крепления,** а не
  строками:
  - каждая точка входа (маршрут, страница, job, команда) вызывается хотя бы
    одним тестом capability — по журналу вызовов (`journal` и `spec-claims`),
    а не по покрытию: покрытие говорит «выполнилось», а не «заявлено»;
  - каждый каталог кода — в модуле модели, каждый пакет разрешён модулю и
    импортируется;
  - каждый файл и экспорт достижим из точки входа (`deadCode`, knip);
  - каждая переменная окружения объявлена и читается (`envVars`).

  Существующее незаявленное — исключения с issue, а не удаление.
- **Тест — решению, а не каждой строке,** внутри точки входа тоже. Тест
  нужен, когда верны все три: это решение (могло быть иначе), поломку не
  заметят (не ловят типы, не видно глазами), ошибка дорогая (общий код,
  данные, деньги, внешние системы). Не тестирую гарантии компилятора и
  библиотек, стили и раскладку, тексты подписей — кроме регрессии после
  реального бага. Бедная страница спеки — не повод тестировать мелочи: тест на
  мелочь падает от любой правки, его правят механически, и спекой он быть
  перестаёт.
- **Исключения — с храповиком:** только в `exceptions.ts` папки решения,
  каждое — элемент, `#issue` и причина; исключение, которое больше не
  нарушает, валит проверку («убери исключение»). Отключение линта в коде —
  только с правилом и `-- #N причина` (`lintExceptions`); общий
  `eslint-disable` запрещён, лишнее отключение — ошибка `lint`. Исключения
  видны на странице решения — это долг, а не тайна.
- **Непроверяемое спекой не называется.** Где вид или UX — решение,
  проверка точечная: скриншот-тест, axe, бюджет производительности, тест
  job'а; остальное (вид, тексты, впечатление) — продуктовый документ или
  приёмка в issue.
- **Названия — утверждения по-русски.** `describe` — возможность на языке
  пользователя («историю видит только тот, у кого есть право на саму
  сущность»), `it` — конкретный пример; не имя функции, компонента или файла
  (`spec-doc --strict` называет такие). Тесты одной возможности из юнитов и
  e2e — под одинаковым `describe`. JSDoc перед `describe` или `it` — то,
  чего не видно из названия, одна-три фразы для читателя спеки; имена
  файлов, номера issue, устройство теста — в `//`, это для читателя кода.
  Непонятное название переписать, а не объяснять.
- **Намерение входит через issue:** реализацию обсуждаем и решения
  принимаем в задаче («## Вопросы», комментарии). У задачи с кодом при
  создании — метки решений (раздел «Ведение задач») и «## Сценарии»: будущие
  названия `it` (или «describe › it») списком. Агент пишет сначала проверки
  — коммит красный — и открывает черновой PR: его раздел «Спека»
  (`spec-diff --scenarios` сверяет сценарии с тестами) пользователь видит до
  кода и может остановить (в режиме «делай полностью сам» ответа не ждать);
  потом код — зелёный.
- **Дифф проверок в PR — дифф спеки,** дифф кода — реализация. Тело PR —
  вывод `spec-diff`: добавленные, изменённые и удалённые названия тестов,
  изменения модели архитектуры, исключений и реестров. Удалённый тест —
  снятое требование, это должно быть видно.
- **Документация генерируется,** руками не пишется: `spec-doc` строит
  страницу на решение (зачем — `<папка>.md`, что верно — `describe`, чем
  проверено — тесты, свёрнутые под разделом; у стандарта — код примеров и
  исключения), страницу архитектуры из модели (схемы C4 и таблица модулей) и
  сиквенс-схемы из трасс сценариев. `docs/spec` в `main` нет: после мержа CI
  публикует её в ветку `spec` (`spec-publish`), ревью идёт по `spec-diff`.
  Продуктовые документы (видение, решения бизнеса, исследования) — не спека
  и живут отдельно.
- **Повторяющееся решение — стандарт:** при закрытии задачи (проверка 5 в
  «Актуализация блока») найденный повтор становится issue «Стандарт · …»,
  результат — правило в `tests/standards/` и рефакторинг.
- **Чего нет:** маркеров состояния и todo как плана (план — в issue), ADR
  (причина — в `<папка>.md` решения), реестров capability, рукописной
  документации о поведении и рисованных схем, Gherkin, мутационного
  тестирования (шум эквивалентных мутантов, давление к тестам на мелочи),
  точек утверждения кроме issue.

## Тесты и код

- **Упал тест — чиню корень** (тест или логику), даже если падение не связано
  с моими правками и зелёный повтор есть; не «пре-существующая флака», не
  таймауты и ретраи: гонку убираю по причине (ждать реального события, не
  паузы; заходить сразу на канонический URL). Подозрение на флаку сверяю тем
  же прогоном на базовой ветке: красно и там — сравниваю дельту, иначе чужая
  флака станет моей регрессией.
- **Регрессионный тест и сторож «дефекта/предупреждения нет» обязаны уметь
  упасть** — как любая проверка решения: откатываю фикс, вижу красный, возвращаю. Не упал при откате —
  либо стережёт от перекоррекции (так и называю), либо удаляется. Тест,
  который не может упасть, хуже отсутствующего.
- **Контракт внешнего API — по схеме или документации**, не по интуиции о
  REST. Зелёный тест может фиксировать неверное поведение: при расхождении со
  схемой чиню тест, а не код под тест.
- **Намеренно разное поведение в двух местах** — встречные комментарии с
  причиной в обоих, иначе следующий читатель «починит».
- **Проверяю то, что дошло до человека,** а не свой выход: доставленное
  письмо, страницу у получателя, обещанный текст в результате (`git grep` и
  глазами). Чужая система меняет результат после нас, свои проверки при этом
  зелёные. Компонент на нескольких поверхностях (сайт и письмо) проверяю в
  изоляции каждой: тестовая страница со стилями сайта врёт про письмо.

## Прод и отладка

- **Прод-база — только чтение.** Изменения данных и схемы — миграцией в PR
  штатной выкаткой. DDL на проде — только по прямому указанию владельца:
  миграция файлом в репозитории, попытка применить, при отказе окружения —
  объяснить, не искать обход. Данные под управлением приложения (роли,
  права, настройки с аудитом) прямым DML не менять — теряется аудит и
  обходятся гарды; чего нет в UI — код-чендж, а не DML.
- **Прод-цифры — сначала та ли база:** первым запросом сверить её с
  репозиторием (число применённых миграций, колонки последних миграций,
  порядок объёмов); не сходится — стоп, не докладывать. Неверные цифры
  рождают неверные решения и задачи.
- **«Не помогло» → прод-факты, не третье воспроизведение:** локальное
  воспроизведение доказывает только, что в моём окружении всё хорошо. Сначала
  логи реального запроса и прод-данные (строка, `updated_at`, аудит), потом
  новая гипотеза.

## Субагенты и worktree

- **Субагенты не делят грязный worktree.** Агенту, который может ставить
  пакеты или трогать файлы «на попробовать», — изолированный worktree либо
  «только чтение плюс временная папка» с запретом на
  `git checkout/restore/stash/clean` и установку пакетов: «прибраться за
  собой» для него значит откатить всё незакоммиченное, включая чужую работу.
  Несколько агентов в одном worktree — по непересекающимся файлам, без
  git-команд, линтер только по своим файлам, у общих файлов один владелец,
  зависимые группы конвейером. После фан-аута — `git status` и
  `git diff --stat` до продолжения.
- **Временная папка сессии общая с субагентами:** временные файлы и скрипты —
  с уникальным префиксом (задача, роль), иначе субагент молча перезапишет
  одноимённый файл.
- **Свежий worktree пуст по неотслеживаемым файлам** (зависимости,
  `.env*.local`): ставлю и копирую из главного чекаута. Все пути в командах
  и заданиях субагентам ведут в worktree: путь «по памяти» и
  агент-исследователь уходят в главный чекаут, и правка ложится на `main`.
  До и после правки — `git -C <worktree> status`.

## Знание проекта и передача работы

- **Общее — в ai-dev, частное — в тестах проекта.** Правило для любого
  проекта (процесс, git, CI, работа с инструментами) живёт только в ai-dev:
  этот файл, `docs/`, скиллы; в проекте — установленная копия, правится в
  ai-dev. Частное для проекта — в его спеке (раздел «Спецификация —
  решения»): что система делает — `tests/capabilities`, из чего состоит —
  модель `tests/architecture`, каким правилам подчиняется код (стек,
  конвенции, запреты) — `tests/standards`, причина — в `<папка>.md` решения.
  Не общее и не проверяемое механически (эксплуатация, рецепты окружения,
  продуктовые документы) — `docs/` проекта. `AGENTS.md` проекта —
  блок установки и только отличия режима от канона (разрешения, способ
  мержа), больше ничего. Договорённость из чата записываю туда же, а не в
  память агента: память привязана к аккаунту и машине, это кэш, не источник.
- **Стек не пересматриваю** и лишних зависимостей не тащу; мешает — вопрос
  пользователю, не тихая замена. Версии — последние стабильные; вопрос по
  инструменту — сначала его официальная документация (фреймворк и хостинг,
  затем сам инструмент): не предполагаю, а проверяю.
- **Перед паузой или сменой агента — комментарий «Состояние» в issue:** что
  сделано, ветка, что дальше, что блокирует — чтобы любой агент с любого
  аккаунта продолжил с этого места.

## CI: параллельные задачи

Каждая ветка и каждый PR прогоняются независимо; отменяется только свой
устаревший прогон той же ветки. Серийность — лишь там, где есть общий ресурс
(окружение деплоя, общая база, внешний сервис с лимитами). Одна очередь на
весь CI — не решение: тормозит все задачи, а без `queue: max` ещё и отменяет
ожидающие. Фрагменты workflow — `docs/ci-concurrency.md`.

- **Ветки и PR — параллельно:** группа `concurrency` по номеру PR или ветке,
  `cancel-in-progress: true`.
- **`main`, теги, ручной запуск — никогда не отменяются:** их прогоны
  деплоят, прерванный деплой хуже лишнего прогона. Вместо отмены —
  `queue: max` (по умолчанию GitHub держит один ожидающий прогон и вытесняет
  его следующим: третий мерж подряд отменил бы второй).
- **Деплой — очередь на окружение:** у job деплоя группа `deploy-<env>`,
  общая для всех workflow репозитория.
- **CI и деплой — в разных workflow:** `queue: max` несовместим с
  `cancel-in-progress: true`. В одном workflow —
  `cancel-in-progress: ${{ github.event_name == 'pull_request' }}` без
  `queue: max`: деплой не прервётся, но ожидающий прогон может быть вытеснен.
- **Агент чужие прогоны не отменяет и не перезапускает** (`gh run cancel` и
  `gh run rerun` — только свой прогон на своей ветке). Ожидание своих чеков и
  мерж — раздел «Git, PR и мерж».
