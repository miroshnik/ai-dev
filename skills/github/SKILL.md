# github — проект и задачи по канону, а не по памяти

Принципы — `AGENTS.md`, раздел «Ведение задач»; правила целиком (типы,
метки решений, эпики, зависимости, проект, milestones, пять проверок
актуализации блока) — `reference.md` рядом с этим файлом. Руками по
справочнику проекты расходятся (где-то выключен «Item closed», где-то фильтр
прячет задачи с доски), а задача заводится без статуса, приоритета или связи
с эпиком. Скрипт `scripts/github.ts` рядом с этим файлом сверяет проект с
каноном и чинит то, что умеет API, и заводит задачу со всеми полями одной
командой; агент проходит шаги UI и спрашивает подтверждение на
разрушительное. Правка уже созданной задачи (Priority, связи) и milestones —
`reference.md`, раздел «Ручные команды». Механика веток, push и мержа —
раздел «Git, PR и мерж — механика» ниже.

```bash
bun <каталог скилла>/scripts/github.ts project check [--repo owner/repo]
bun <каталог скилла>/scripts/github.ts project fix [--repo owner/repo] [--confirm] [--template owner/N | none]
```

Репозиторий — из `git remote get-url origin` или `--repo`. Нужен `gh` со
scope `project` (`gh auth refresh -s project`); типы issue организации —
`admin:org`.

## Когда что

| Момент | Действие |
|---|---|
| Начало сессии, перед работой с задачами | `project check` — раз в сессию |
| `check` дал ❌ | `project fix` → шаги UI → подтверждения → снова `check` |
| Репозиторий без проекта | `project fix`: привяжет одноимённый проект владельца, иначе скопирует эталон, иначе создаст |
| Облачная сессия | не запускать: Projects v2 ей недоступны (`docs/cloud-sessions.md`), скрипт выходит с кодом 2 |

Коды: `0` — всё по канону (у `fix` — и шагов не осталось), `1` — есть ❌,
шаги или ошибки, `2` — ошибка вызова, доступа или облачная сессия.

## Что проверяется

1. Проект привязан к репозиторию, он один, название = имя репозитория.
2. Представления `Доска` (BOARD, колонки по `Status`), `Таблица` (TABLE),
   `Роадмэп` (ROADMAP), фильтры пусты, других нет.
3. `Status`: `Бэклог` → `В работе` → `Готово`.
4. Поля «Оценка, ч», «Факт, ч», «Токены, млн», «Стоимость, $» (Number),
   своих полей сверх канона нет.
5. Только организация: `Priority` — поле issue организации, подключено,
   `Таблица` и `Доска` сортируются по нему; типы issue — ровно «Задача»,
   «Баг», «Эпик». В личном аккаунте их нет — строка `➖`.
6. Workflow «Item added to project» (→ `Бэклог`), «Item closed»
   (→ `Готово`), «Auto-add to project» (`is:issue is:open`) включены.
7. Закрытые задачи — в `Готово`, закрытые без выполнения (not planned,
   дубль) — вне проекта.
8. Открытые задачи репозитория — в проекте, у каждой есть `Status`.
9. Метки решений — по дереву спеки основной ветки (через API): имя метки —
   имя решения (папка `tests/capabilities|standards|architecture/<name>` или
   модуль модели), вид — цветом: capability `0E8A16`, standard `1D76DB`,
   architecture `D93F0B`. Одно имя у решений разных видов — одна метка: цвет
   старшего вида (capability → standard → architecture), в описании все
   пути. Признак метки решения — описание `Решение: …`. Решение без метки —
   создаётся. Метка без решения на открытой задаче — новое решение (его
   ставит `task new`, в основную ветку оно придёт с PR задачи): строка `○`
   с номерами задач, пункт ✅, метку не трогают. Метка без решения и без
   открытых задач — удаляется с `--confirm`; одна такая и одна недостающая
   того же вида — переименование с `--confirm` (задачи сохраняют метку);
   чужой цвет или описание — правится. Старая метка `вид:имя`
   переименовывается в `имя` сама, есть решение в основной ветке или нет;
   имя уже занято — слияние с `--confirm` (задачи получают метку с именем,
   старая удаляется). Обычная
   метка с именем решения — ❌, меткой решения становится с `--confirm`.
   Модель (`tests/architecture/model.ts`) читает отдельный процесс — не
   загрузилась, метки модулей не трогаются, ❌ с причиной.
10. Мерж в основную ветку — только актуальной ветки с зелёными обязательными
    чеками: действующее правило ветки (`Ref.rules` — ruleset репозитория или
    организации — либо классическая защита) со strict и непустым списком
    обязательных чеков; strict без чеков GitHub не применяет. Нет — `fix`
    ставит ruleset `ai-dev`: `~DEFAULT_BRANCH`, strict, обязательные — чеки,
    зелёные на каждом из последних 10 влитых PR, обход — роль admin (прямой
    push владельца; неактуальный PR — только `gh pr merge --admin`). Свой
    ruleset сверяется и дальше: выключен, без strict или обхода — правится;
    обязательный чек, которого нет у свежей головы (последний влитый PR,
    открытый PR с завершёнными чеками), уходит из списка — иначе PR ждал бы
    его вечно; новый стабильный — добавляется. Чужое правило со strict и
    чеками — ✅, свой не заводится. Приватный репозиторий на Free (GraphQL
    отдаёт пустые правила, REST — 403 «Upgrade to GitHub Pro») и влитые PR
    без общего зелёного чека — строка `➖`. Проект пункту не нужен.

## fix: кто что делает

- **API — сам скрипт:** привязка, копия эталона или новый проект,
  недостающие представления и поля, вид представления, снятие фильтра,
  варианты `Status`, поле issue `Priority`, статусы задач, добавление
  открытых задач, удаление из проекта закрытых без выполнения, метки
  решений (создание, цвет), ruleset основной ветки (создание, правка
  своего). Строки `+`.
- **Шаги UI** (`Шаги в UI …`) — чего нет в API. Вызов `fix` — разрешение на
  настройку проекта этого репозитория: агент проходит шаги сам, браузером,
  где пользователь вошёл в GitHub (Claude in Chrome или встроенный браузер
  после его входа), без отдельного спроса. Нет браузера или входа — список
  шагов со ссылками пользователю. Пароль агент не вводит. После шагов —
  снова `check`.
- **Подтверждение** (`Нужно подтверждение …`) — удаление и переименование в
  проекте, где уже есть задачи, отвязка лишних проектов, типы issue
  организации (они общие для всех её репозиториев), удаление и
  переименование меток решений (они стоят на задачах). Показать список
  пользователю, после «да» — `fix --confirm`. В новом проекте без задач
  удаление и переименование идут без подтверждения.
- **Ошибка** — строка `!` с причиной (и ссылкой на UI, если шаг там
  делается): чаще всего не хватает scope у `gh`.

## Шаги UI — как проходить

- **Workflow:** ссылка ведёт на настроенный workflow
  (`<проект>/workflows/<fullDatabaseId>`) или на список `<проект>/workflows`,
  где ненастроенный выбирается в меню слева. Edit → настройка → **Save and
  turn on workflow**; справа вверху появится `On`. В Set value
  `A value is required` — вариант `Status`, на который смотрел workflow,
  удалён (варианты заменяли без id): выбрать заново.
  - «Item added to project»: триггер `issue, pull request` (по умолчанию),
    Set value → `Status: Бэклог`.
  - «Item closed»: Set value → `Status: Готово`.
  - «Auto-add to project»: репозиторий — этого проекта, фильтр
    `is:issue is:open`, Enter — счётчик «See N existing items» должен
    обновиться. Без `is:open` обновлённая закрытая задача (и not planned)
    вернётся в проект. Уже существующие задачи auto-add не добавляет — их
    добавляет `fix`.
- **Сортировка по Priority, колонки доски:** представление → кнопка `View`
  справа → `Sort by: Priority` / `Column by: Status` → `Save view` →
  диалог «Save display options for …?» → `Save`. Escape закрывает диалог
  без сохранения: сортировка остаётся только в URL (`?sortedBy…`), а
  маркер несохранённого у вкладки врёт — итог проверяет `check`.
- **Поля issue организации** (`Priority` нет в организации) — настройки
  организации по ссылке из шага, затем снова `fix`.

## Детали, из-за которых скрипт написан

- **Workflow через API не включить и цель не прочитать:** `ProjectV2Workflow`
  отдаёт только `name`, `number`, `fullDatabaseId`, `enabled`; мутации
  включения нет. Ненастроенного workflow нет в списке вовсе (у нового
  проекта — «Item closed», «Pull request merged», «Auto-close issue»).
- **Цель «Item closed» видна по результату:** закрытая задача не в `Готово` —
  workflow выключен или смотрит на удалённый вариант `Status`. `fix` ставит
  `Готово` и оставляет шаг проверить цель в UI.
- **Варианты `Status` переименовываются с тем же id**
  (`updateProjectV2Field`, `singleSelectOptions[].id`): значения задач и
  цель «Item closed» сохраняются. Замена вариантов без id даёт новые id —
  статусы задач пропадают, «Item closed» ставит удалённый `Done`.
- **Эталон** — проект ai-dev (`miroshnik/6`): в нём один раз настроено всё,
  чего нет в API. Копия (`copyProjectV2`) переносит представления с
  настройками, поля и настроенные workflow, кроме auto-add; не переносит
  задачи, соавторов и привязку к репозиторию. Эталон недоступен (чужой
  аккаунт) или `--template none` — проект создаётся с нуля
  (`createProjectV2`) и доводится через API: `Todo / In Progress / Done` →
  канон с теми же id, `View 1` → `Таблица`, остальное создаётся.
- **Фильтр представления пуст:** `iteration:@current` без поля Iteration
  молча прячет задачи с доски.
- **`Priority` — поле issue организации** (`isIssueField`), а не своё поле
  проекта с тем же именем. Сортировку API читает (`sortByFields`), но не
  задаёт; группировку доски — тоже (`verticalGroupByFields`).
- **Проект, которым пользовались** — в нём есть задачи.

## Задачи — task

```bash
bun <каталог скилла>/scripts/github.ts task new --title "…" [--body-file F | --body "…"] [--type Задача|Баг|Эпик] \
    [--epic N] [--milestone "…"] [--blocked-by N,N] [--priority Urgent|High|Medium|Low] \
    [--labels <решение>,<вид>:<новое решение>,<метка>] [--repo owner/repo]
bun <каталог скилла>/scripts/github.ts task status <N> "В работе"      # Бэклог | В работе | Готово
bun <каталог скилла>/scripts/github.ts task drop <N> [--duplicate-of M]
bun <каталог скилла>/scripts/github.ts task close <N> [--no-git]         # после мержа PR: факт, Готово, эпик, milestone, ветка долой
bun <каталог скилла>/scripts/github.ts pr labels <PR>                 # метки решений по диффу PR
bun <каталог скилла>/scripts/github.ts pr queue [<PR> | --head <ветка>] # голова ли PR в очереди мержа
```

| Момент | Действие |
|---|---|
| Новая задача, подзадача эпика, эпик | сначала — нет ли такой (`gh issue list --search`); `task new`; затем оценка — скилл `est` (эпик не оценивается: его «Оценка, ч» — сумма подзадач, `reference.md`) |
| Взял в работу · переоткрыли | `task status N "В работе"` |
| PR смёржен / задача закрыта без PR | `task close N` — факт (`est`), `Готово`, эпик и milestone, влитая ветка долой; затем актуализация блока — субагентом (пять проверок — `reference.md`, «Актуализация блока при закрытии задачи») |
| Не будем делать, дубль, заменена другими | `task drop N [--duplicate-of M]` |
| PR готов (и после новых коммитов) | `pr labels <PR>` — метки решений задаче и эпику |
| Перед push ветки и ожиданием CI | `pr queue` — не голова (код 1): ребейз локально, push — после мержа PR впереди |

**`task new`** — одна мутация `createIssue`: тип issue организации (в личном
аккаунте для «Эпик» — метка `epic`, нет метки — создаётся; «Задача» и «Баг»
там без метки), проект, эпик (sub-issue), milestone по названию среди
открытых, `Priority` в организации (`Medium` по умолчанию). Затем
`Status: Бэклог` — сам, не дожидаясь workflow, — и blocked by. Заголовок
подзадачи получает префикс эпика (`<Префикс> · …`), если его нет; эпику
поднимается `Priority` до подзадачи, если она срочнее. Всё проверяется до
создания — ошибка (код 2) не оставляет задачу наполовину: `--epic` — открытый
эпик, milestone есть, блокеры есть (закрытые пропускаются), открытой задачи с
тем же заголовком нет, тип включён, `Priority` — из вариантов; в личном
аккаунте `--priority` — ошибка. `--labels` — метки задачи в той же
мутации: решение из основной ветки — по имени (`billing`), новое решение —
`вид:имя` (`capability:export`, метка — `export`, строка «новое решение»: оно
появится в PR задачи); нет метки решения — создаётся с цветом вида; обычная
метка должна существовать, иначе ошибка до создания. Выводит `Создана #N …`,
строки `+` и следующий шаг.

**`task status`** — ставит `Status` (задача вне проекта — добавляется).
Подзадача «В работе» — эпик из `Бэклог` тоже «В работе». Подсказки: эпик
закрыт, а подзадача снова в работе — переоткрыть эпик и его milestone; все
подзадачи закрыты — закрыть эпик и поставить ему `Готово`.

**`pr labels`** — метки решений по изменённым файлам PR (API):
`tests/capabilities|standards|architecture/<name>/…` — метка решения, файл
кода — метка модуля модели из головы PR (самый длинный подходящий каталог),
`tests/lib` и файлы вне модулей — не решения. Механическая правка решение
не меняет и метку не даёт: удалённый файл, переименование без правки
содержимого, `exceptions.ts` папки решения — решение, тронутое только так,
выходит строкой `○` (нужна метка — поставить руками). Ставит задачам из
«Closes #N» (связь PR с задачами; сразу после создания PR GitHub её ещё не
проставил — задачи из ключевых слов тела PR, как их понимает GitHub; нет ни
одной — ошибка), недостающую метку создаёт с цветом вида; прежнюю метку
решения, которого нет в диффе, не снимает — строка `=`. Эпик задачи
получает те же метки — объединение подзадач; так же при `task new --epic
--labels`.

**`task drop`** — закрывает как not planned (с `--duplicate-of` — как дубль
со ссылкой) и убирает из проекта: иначе «Item closed» запишет её в `Готово`
и в оценку эпика. Выполненную не трогает. Подзадача — подсказка пересчитать
«Оценка, ч» эпика.

**`task close`** — ритуал закрытия одним вызовом, а не по шагу на ход на
самом большом контексте сессии. Только после мержа PR задачи (или закрытия
без PR): PR открыт или закрыт без мержа — ошибка до изменений. GitHub
бывает часами не связывает влитый PR с задачей — тогда PR задачи ищется
среди последних PR основной ветки по ветке `<type>/<N>-<slug>` и «Closes
#N» в теле: влитый — задача закрывается с комментарием «Закрыта по PR #M:
GitHub не связал PR с задачей», нет — отказ с перечнем проверенного
(`gh issue close` руками не нужен). Порядок:
закрыть задачу, если влитый PR её не закрыл; факт — `est fact <N> --write`
скриптом est рядом (`../est/scripts/est.ts`; нет — строка `○ факт
недоступен`, упал — его ошибка строкой `!`, остальное делается); `Status`
«Готово»; закрыт последний sub-issue — эпик закрывается и получает «Готово»;
в milestone задачи (и эпика) не осталось открытых — milestone закрывается
(REST); влитая ветка — по пункту «Сразу после мержа PR» раздела «Git, PR и
мерж — механика» ниже: чекаут с ветки
задачи — на `origin/<base>` detached, локальная и удалённая ветка удаляются;
не влита, чужая или каталог — не чекаут репозитория — строка `○`, ничего не
трогается; worktree сессии команда не удаляет — подсказка `Дальше`. `--no-git`
— без git-шага. Последней строкой — оба шага конца сессии: актуализация
блока субагентом со свежим контекстом (`reference.md`, «Актуализация блока
при закрытии задачи») и после неё — последняя строка ответа «Всё сделано.
Сессию можно закрывать.», а если что-то осталось — «Осталось: …». Облачная
сессия — отказ с объяснением (`docs/cloud-sessions.md`).

**`pr queue`** — очередь мержа основной ветки (раздел «Git, PR и мерж —
механика» ниже):
каждый мерж делает остальные ветки отставшими, и их push до чужого мержа —
прогон CI впустую. Голова — открытый PR в основную ветку, который не
отстаёт от неё и у которого CI зелёный или идёт (чеков ещё нет — тоже идёт);
из нескольких — меньший номер. Отставший, красный PR, черновик и PR без
ветки очередь не держат — строки `○`. Без аргумента — PR текущей ветки
(`--head` — другой ветки); PR ещё нет — впереди все PR очереди. Код `0` —
голова: ребейз, push, CI и мерж твои, строка «за тобой» — кому после мержа
написать «влит, твоя очередь»; `1` — не голова, `⚠` называет PR впереди:
ребейз только локально, push — после их мержа; `2` — ошибка (номер — не
открытый PR в основную ветку). Пропустить вперёд — перевести свой PR в
черновик (`gh pr ready --undo <N>`), вернуться — `gh pr ready <N>`.

## Git, PR и мерж — механика

Принципы — `AGENTS.md`, раздел «Git, PR и мерж»; здесь — правила целиком.
Ожидание чеков, полный SHA и мерж, который выкатывает, — `docs/pr-checks.md`.

- **Подъехал чужой PR** — сразу `git fetch && git rebase origin/main`
  локально, не дожидаясь конфликта; push после rebase — только в свою
  очередь мержа (пункт ниже) и `git push --force-with-lease` (не `--force`),
  с разрешением как обычно. Отставшую ветку и ветку с красным
  обязательным чеком GitHub не вольёт: ruleset основной ветки (strict и
  обязательные чеки) ставит `github project fix`; обход —
  `gh pr merge --admin` — только по прямому указанию владельца.
- **Несколько PR одного репозитория ждут мержа — очередь.** Ребейз на
  `origin/main` с push, CI и мерж — только у головы очереди; остальные
  ребейзят локально и не пушат до своей очереди: push до чужого мержа —
  лишний прогон CI, после мержа ветку всё равно ребейзить. Голову перед
  push и ожиданием CI называет `github pr queue`: открытый PR, который не
  отстаёт от основной ветки и чей CI зелёный или идёт, из нескольких —
  меньший номер; отставший, красный и черновик очередь не держат. Не голова
  (код 1) — не пушу, жду мержа PR впереди. Голова после мержа пишет
  следующему «влит, твоя очередь»; не готовая к мержу — переводит свой PR в
  черновик и так пропускает вперёд.
- **Перед push** — `git branch --show-current` (своя ветка, а не локальный
  `main`: после серии checkout и rebase push уходил мимо PR), `git fetch` и
  `git rev-list --count HEAD..origin/main`;
  не 0 — rebase и повторная проверка того, что зависит от общего состояния
  (нумерация миграций и решений, общие списки); затем очередь мержа —
  `github pr queue` (пункт выше).
- **Сразу после мержа PR — влитое удаляю целиком, без спроса** (шаг
  `github task close`): чекаут сессии с влитой ветки долой —
  `git fetch --prune && git switch --detach origin/main && git branch -D <ветка>`,
  удалённую ветку — `git push origin --delete <ветка>`, если хостинг не
  удалил сам, свои worktree и временные ресурсы сессии (базы, контейнеры).
  «Влито» — по PR (`gh pr view <N> --json state` = `MERGED`) или
  `git cherry origin/main <ветка>`, не `git branch --merged`: после squash
  или rebase git не видит, что ветка влита, — панель сессии и `git status`
  зовут на второй PR, push в ней воскресит удалённую. Чужие ветки и worktree
  живых сессий не трогаю, невлитое — никогда. Следующая задача — новая ветка
  от `origin/main`.
- `gh pr merge --delete-branch` из worktree локальную ветку не удаляет
  (старый gh падает с `'main' is already used by worktree`) — это не ошибка
  мержа: проверяю `gh pr view <N> --json state`, merge не повторяю.
