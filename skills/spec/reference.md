# spec — почему так

Справочник к `SKILL.md`: обоснование решений и детали разбора.

## Форматы отчётов

- JSON Vitest и Jest — один формат (`testResults[].assertionResults[]`), JSON
  Playwright — своё дерево `suites → specs → tests` с проектами и аннотациями
  (причина `skip` есть только там). Формат определяется по содержимому файла,
  не по расширению; несколько отчётов сливаются по ключу теста.
- `bun test` JSON-отчёта не имеет, зато отдаёт JUnit XML (`--reporter=junit`):
  файл — `testsuite` с `name = file`, describe — вложенные `testsuite` с
  атрибутом `file`, тест — `testcase`; `<skipped/>` — пропущен,
  `<skipped message="TODO"/>` — todo. XML разбирается регулярными выражениями
  со стеком suite: у Bun и Node нет XML-парсера без зависимостей, а формат
  прост. Сущности `&amp;`, `&lt;`, `&#…;` раскрываются.
- pytest и Python не поддерживаются намеренно: стек — TypeScript и Bun
  (issue #27, вопрос 1).

## spec-diff: статический разбор, не два отчёта

- Отчёт требует прогона на двух ревизиях: чекаут базы (или второй worktree),
  установка зависимостей, полный прогон — минуты и побочные эффекты, а нужны
  только имена. Статический разбор берёт файлы через `git show <rev>:<path>`
  за секунды и работает в CI на PR без второго прогона.
- Цена — сканер вместо раннера: динамические имена (`it.each`, переменная
  вместо строки) видны с плейсхолдером или не видны вовсе. Для правила
  «`it` — пример по-русски» это редкость, а `describe`/`it` со строковыми
  литералами разбираются надёжно.
- Сканер не парсер: он различает строки, шаблоны с `${…}`, комментарии и
  скобки, считает глубину `{}`, а телом `describe` считает первую `{` после
  `=>` или `function(...)` на уровне аргументов вызова — объект опций
  (`describe("x", { timeout }, () => …)`) телом не считается. Полный парсер
  (TypeScript API, acorn) — зависимость, которой скилл избегает.

## Проза из JSDoc

- Название теста — требование, но имя папки (`est`) и `describe` («Калибровка
  k») не говорят, что это и зачем. Проза нужна, и живёт она рядом с тестом:
  отдельный рукописный документ о поведении расходится с тестами, а правило
  «Спецификация — тесты» такого документа не допускает.
- JSDoc, а не `//`: разделение уже принято в TypeScript — `/** */` описывает
  для потребителя (подсказки редактора, сгенерированные доки), `//` —
  заметка для читателя кода. Причины решений и отвергнутые альтернативы
  остаются в `//` и в документацию не утекают.
- Отчёты раннеров комментариев не несут, поэтому `spec-doc` читает исходники
  тем же сканером, что `spec-diff`, и связывает прозу с тестом по цепочке
  имён. Отдельный файл описания в папке capability (README рядом с тестами)
  отвергнут: второй источник того же смысла, который никто не сверяет с
  тестами.
- `spec-diff` прозу не сравнивает: требование — название теста; правка прозы
  видна в диффе `docs/spec`, который коммитится с PR.
- Проза теста — цитатой внутри пункта списка: абзац через пустую строку
  сделал бы список «рыхлым» (отступы между всеми пунктами), а строка без
  разметки слилась бы с названием в один абзац.
- Строки «раздел · путь · N тестов» под заголовком нет: раздел и путь
  следуют из конвенции, статус виден у каждого теста; в индексе остались
  только пропущенные и падающие — то, на что надо смотреть.

## Запуск — Bun

- `bun script.ts`: TypeScript без сборки и без `package.json` рядом — скилл
  лежит в `~/.claude/skills` или `~/.agents/skills`, где ничего не собрать.
- Скрипты используют только `node:`-API (`fs`, `path`, `child_process`,
  `util.parseArgs`) — без `Bun.*`, поэтому идут и под Node ≥ 22.18 (стираемый
  синтаксис: без `enum`, `namespace` и parameter properties, импорт с `.ts`).
- Тесты скилла — `bun test` (импорт из `bun:test`; импорты из `vitest` он
  тоже понимает): накладные расходы раннера 0,01 с против 0,3 с у Vitest на
  файл, Node в CI не нужен. Скрипты в тестах запускаются через `bun` — то, что
  запускает пользователь.

## Идентичность и переименования

- Ключ теста — путь папки + цепочка `describe` + имя. Файл в ключ не входит:
  правило говорит о папке как единице спеки, перенос тестов между файлами
  одной capability не меняет требований.
- Переименование ищется только в том же файле — в двух шагах: (1) тот же
  `describe`, похожее имя, похожесть ≥ 0,6 по Ratcliff/Obershelp (как
  `difflib.SequenceMatcher.ratio`), жадно по убыванию похожести; (2) то же
  имя, другой `describe` — переименован `describe`. Порог высокий намеренно:
  спрятать снятое требование под видом переименования хуже, чем показать
  переименование как удаление и добавление.
- Merge-base по умолчанию — чтобы дифф совпадал с тем, что показывает PR на
  GitHub, и тесты, добавленные в `main` параллельно, не выглядели удалёнными.

## Детерминизм

- Ни таймстампов, ни длительностей, ни абсолютных путей в выводе; порядок —
  папки по имени, файлы по пути, тесты в порядке объявления (отчёт внутри
  файла отдаёт их в этом порядке; Vitest в concurrent-режиме — нет, тогда
  порядок берётся из отчёта как есть).
- Одинаковые тесты из нескольких отчётов (два проекта Playwright, два прогона)
  сливаются; статус — худший (`failed` > `passed` > `todo` > `skipped`,
  «все пропущены» — пропущен).
- Маркер в первой строке файла — единственный признак «это мой файл»: скрипт
  удаляет только такие и не трогает рукописные в тех же каталогах.

## Что не делается

- Нет конфигурации под репозиторий: дерево `tests/` из правила, каталог
  вывода `docs/spec`, форматы отчётов — всё по умолчанию; менять можно
  только флагами (`--root`, `--out`, `--base`).
- Нет оценки тестов: падает/пропущен — сказал раннер, скрипт лишь показывает.
- Нет генерации справочной документации (схема, маршруты, окружение) — это
  другие генераторы из кода, не из тестов.
