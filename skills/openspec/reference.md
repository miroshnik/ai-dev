# OpenSpec: ловушки и ограничения инструмента

Проверено на OpenSpec 1.4.1 (2026-06); поведение парсера и валидатора
зависит от версии — после обновления CLI перепроверять. CLI ставится
глобально или в devDependencies; версия — `openspec --version`.

## Команды

```bash
openspec new change <name>                       # новый чейндж
openspec instructions <artifact> --change <name> # шаблон и инструкция по артефакту
openspec status --change <name>
openspec validate <name> --strict                # один элемент
openspec validate --changes --strict --no-interactive   # все активные чейнджи
openspec validate --specs --strict --no-interactive     # все главные спеки
openspec archive <name>                          # синк дельт в главные спеки + перенос в changes/archive/
```

## Парсер дельт: что захардкожено

- Токены не настраиваются через schema: `## ADDED|MODIFIED|REMOVED|RENAMED Requirements`
  (уровень 2), `### Requirement:` (уровень 3), `#### Scenario:` (ровно
  четыре решётки); в теле требования обязательно литеральное `SHALL` или
  `MUST`. Переименованный токен проходит `schema validate`, но молча
  ломает `validate` и `archive`.
- **Два раздела `## MODIFIED Requirements` в одном delta-spec** — второй
  затирает первый при `archive` (секции кладутся в объект по заголовку);
  `validate --strict` этого не ловит и возвращает 0. Все MODIFIED — под
  одним заголовком; `## RENAMED Requirements` — отдельной секцией.
- `MODIFIED` заменяет блок требования **целиком**: сценарии, которых нет
  в дельте, исчезают без предупреждения. Отсюда правило «смена смысла —
  REMOVED + ADDED».
- Сопоставление имён требований при архивации чувствительно к регистру,
  нормализуется только хвостовой пробел.

## Архивация перестраивает файл спеки

- `archive` сохраняет всё **выше** `## Requirements` и хвостовые разделы
  `## …`, а внутри `## Requirements` удаляет всё, что не является блоком
  `### Requirement:`. Собственные разделы (решения, обоснования) держать
  выше `## Requirements` или в хвостовом разделе.
- **Первый архив новой спеки** строит главный файл из одной дельты
  `ADDED`: frontmatter, разделы решений и обоснований пропадают, `## Purpose`
  становится заглушкой «TBD». Долгоживущее содержимое хранить вне
  `openspec/specs/` (например, в каталоге стандартов или решений
  репозитория), либо перезаполнять после первого архива.
- Контракт главной спеки: `## Purpose` + `## Requirements`, ≥ 1 требование
  с SHALL/MUST, ≥ 1 `#### Scenario:`; требование вне `## Requirements` или
  заголовок дельты в главной спеке — ошибка.

## validate --strict

- Жёсткие ошибки (падают и без `--strict`): нет `## Purpose` или
  `## Requirements`, требование без SHALL/MUST, требование без сценария.
- Только под `--strict`: `## Purpose` короче 50 символов. `## Why` короче
  50 символов и больше 10 дельт в чейндже strict **не** валят (вопреки
  документации некоторых версий).
- Неизвестные поля YAML-frontmatter в спеке `--strict` терпит.
- `validate` использует встроенные схемы и константы, `schema.yaml` не
  читает; `openspec schema validate` проверяет только синтаксис yaml,
  существование шаблонов, отсутствие циклов в `requires` и id артефактов;
  имя `template:` должно совпадать с файлом на диске.

## Доставка инструкций агенту

- `openspec update` пишет обобщённые обёртки скиллов и команд без текста
  схемы; текст шаблона доходит до агента только через
  `openspec instructions <artifact> --change <id>`. Проверка:
  `openspec new change probe && openspec instructions specs --change probe`.
- `instructions` выдаёт два блока: `<template>` (каркас для заполнения) и
  `<instruction>` (как писать). Свои указания класть в `instruction:`
  артефакта, `template:` держать чистым каркасом — иначе агент копирует
  инструкцию в спеку.

## Ошибки процесса, которые уже случались

- Архивация при незакрытых задачах (`--yes` заглушил предупреждение) →
  спеки описали то, чего в проде нет → `git revert` и повторный архив
  вторым PR.
- Отдельный коммит с архивом поверх уже запушенной ветки → второй полный
  прогон CI; забытый архив оставался незапушенным после мержа.
- Правило проекта об имени ветки записано в памяти неверно → отклонённый
  push: имя ветки, scope коммитов и обязательные проверки читать из хуков и
  `config.yaml` репозитория, а не из памяти.
