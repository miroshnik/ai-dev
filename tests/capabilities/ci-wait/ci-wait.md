Скилл `ci-wait`: агент дожидается исхода всех чеков PR или коммита одним скриптом — PASS, FAIL, TIMEOUT или
ERROR, — а не угадывает по первому ответу GitHub, что CI прошёл.

Сразу после push чеков ещё нет, и «пусто» легко принять за «прошли»; поздний чек регистрируется, когда первые
уже зелёные. Поэтому пустой список — ожидание, а PASS засчитывается, только когда снимок без pending
повторился два опроса подряд.

У коммита (прогон на `main` после мержа, деплой) чеки лежат в двух местах: commit statuses пишут внешние
сервисы и хостинги, check-runs — GitHub Actions. Ожидание по одним статусам висело до таймаута на коммите, где
весь CI — Actions, поэтому `status <sha>` ждёт оба вида, а `--context` ищет чек по имени в обоих. `pr <N>`
ждёт так же — по SHA головы PR, перечитывая её каждый опрос.

`merged <N>` ждёт чеки коммита мержа PR, беря его SHA из PR (#285): после мержа SHA добывали отдельными ходами
`gh pr view` на пиковом контексте сессии — замер показал их в 10 закрытиях из 17. С номером PR ожидание
запускается тем же ходом, что `github task actualize`. Невлитый PR — ERROR сразу: ждать нечего.

Одноимённые check-runs коммита сводятся к последнему (#319): на одном SHA лежат check-runs всех прогонов — прогон,
отменённый новым push, остаётся и после того, как голову вернули на прежний коммит (проверка поломкой), — и
отменённый ранний давал ложный FAIL при зелёном последнем. Итог — за check-run с наибольшим `id` у пары «имя,
приложение», как у обязательных чеков GitHub; одноимённые чеки разных приложений — разные чеки. Статусы API
сводит к последнему на контекст сам.

Упавший чек завершает ожидание сразу (#246): рядом с ним бывает долгий превью-деплой, и сессия узнавала о
красном CI на десятки минут позже, а монитор CI приложения без Auto-fix её не будит. Полный снимок — флагом
`--wait-all`.

PR с конфликтом с базой — сразу ERROR: GitHub не создаёт merge-ref, workflow на `pull_request` не запускаются,
и ожидание кончалось итогом по одним статусам хостинга — с прошедшим деплоем это был бы PASS без единого
прогона CI. По той же причине обязательные чеки базовой ветки (ruleset и классическая защита) ждутся по
именам: незарегистрированный обязательный — не финал.

Только REST: `gh pr checks` ходит в GraphQL, его квота общая на все параллельные сессии пользователя и
кончалась, давая ERROR при нормально идущих чеках. Лимит REST — ожидание до сброса квоты, а не ERROR.

Сбой `gh` — не исход (#330), и в запросах до первого опроса: проверку коммита у `status` делал один запрос
без повтора, и во время инцидента GitHub разовый сбой давал «коммит не найден», код 3, при существующем коммите —
сессия читала ERROR как неверный вызов. «Не найден» — только ответ API «нет» (422 «No commit found», 404), иной
сбой — повтор, как в опросе, ERROR — после пяти подряд. Так же обязательные чеки базовой ветки: «нет» — только
403 (нет прав читать правила) и 404, разовый сбой больше не стирает их до конца ожидания.

`issue <N>` ждёт закрытия issue (#282): красный `main` чинит одна сессия по багу «`main` красный…» (`github pr
premerge`, код 3), остальные ждут его закрытия — фоновой командой, чьё завершение будит сессию, а не опросом
руками. Закрытый issue — PASS сразу: повторный опрос нужен поздно регистрирующимся чекам, а не issue.

Отвергнуто: `gh run watch` видит только Actions и не видит статусы хостинга; `gh pr checks` не принимает SHA и
тратит квоту GraphQL; `sleep` в цикле без исходов не отличает «не зарегистрирован» от «прошёл»; число
ожидаемых чеков из прошлого прогона ветки — набор чеков законно меняется (фильтры путей workflow), счёт по
прошлому прогону давал бы ложный TIMEOUT.
