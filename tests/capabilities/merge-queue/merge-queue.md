Скилл `github`, `pr queue`: несколько сессий одного репозитория вливают PR по очереди — ребейз с push, CI и
мерж только у головы очереди, остальные ребейзят локально и ждут.

Каждый мерж в основную ветку делает остальные ветки отставшими: strict-правило основной ветки их не вольёт, а
ребейз с push перезапускает CI. Четыре параллельные сессии одного репозитория ребейзили и пушили друг за другом, и
каждый чужой мерж отправлял их прогоны CI в мусор. Команда называет голову по состоянию GitHub, без переписки
сессий: открытый PR в основную ветку, который от неё не отстаёт и у которого CI зелёный или идёт; из нескольких —
меньший номер. Отставший, красный PR и черновик очередь не держат — им сначала ребейз или починка; чтобы пропустить
вперёд, свой PR переводят в черновик.

Отвергнуто: merge queue GitHub — только у репозиториев организации, личный аккаунт её не получает; порядок по
времени зелёного прогона — меняется при каждом перезапуске и требует читать прогоны; метка очереди — её ставят и
снимают руками и забывают; одна переписка сессий — договорённость без проверки, новая сессия о ней не знает.
