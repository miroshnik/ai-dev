Установка флоу: одна команда `bunx github:miroshnik/elves install` ставит проекту флоу последнего релиза Elves для
любого агента — тонким, без копии; с `-g` машина получает канон, скиллы и хук.

Проект тонкий (#552). Копия флоу в `.agents/` стоила дорого: обновление — отдельная задача и PR на тысячи строк (в
одном проекте 9 обновлений за 15 дней, до +5,8k/−2,7k строк за раз), плюс исключения в `.gitignore`, линтерах и
форматтерах. Теперь в репозитории — только версия пакета `@miroshnik/elves` в `devDependencies` (харнесс тестов,
spec-скрипты и CI проекта — его версии: `bun install` приносит её в CI, коллеге и облачной сессии), манифест
`.agents/elves.json`, шим очереди `.agents/slot.sh` и блок в `AGENTS.md` со ссылкой на канон машины; канон и скиллы
живут на машине. Обновление проекта — подъём версии, несколько строк в ветке текущей задачи. Версия — точная, релиза,
которым идёт установка (тег `v2026.10.15.1` — `2026.1015.1`): это версия проекта, и `check` сравнивает её с релизом.
`install` пишет её в `package.json` и зовёт `install` менеджера пакетов проекта — тот обновляет свой lockfile; без
lockfile — только `package.json` и строка с командой: lockfile, которого проект не держит, установка не заводит.
Менеджер не смог (нет сети, песочница агента) — предупреждение с командой: `package.json` уже верный. Проект без
`package.json` версии не получает — закреплять нечего. Установщик из клона или пускатель из `main` без релизов — не
релиз: версию не знает, `devDependency` не трогает и говорит об этом (#558, вопросы 1 и 5). Отвергнуто: версия в
манифесте — её уже закрепляет `devDependencies`, по нему `bun install` и ставит пакет; `bun add`, `npm i -D` и
другие по менеджеру — четыре разные команды, а правка `package.json` и одна команда `install` — для всех.

Проект с копией прошлого релиза `install` и `update` переводят на тонкий: копия `.agents/elves/` (и под прежним именем),
скиллы флоу из манифеста в `.agents/skills`, симлинки на них в `.claude/skills` и правил в `.claude/rules`, поля копии в
манифесте и её исключения в `.gitignore` уходят; свои скиллы проекта остаются (#558, вопрос 6). Импорты харнесса,
модели архитектуры, фрагмента ESLint и github из копии в тестах и конфигах ведут в `exports` пакета
(`@miroshnik/elves/spec/harness` …), скрипты spec копии — в `elves <скрипт>` в `package.json` и в
`bun --no-env-file node_modules/.bin/elves <скрипт>` в CI: шаг GitHub Actions не видит `node_modules/.bin`, а
`bunx elves` без пакета в node_modules скачал бы из npm чужой пакет `elves` (#558, вопрос 2); репортёр knip
`knip-hints.cjs` — файлом пакета, в `exports` его нет. Что ещё называет `.agents` — исключение `.agents/**` в линтере
или форматтере, путь в копию, которого правило не знает, — установка называет строкой с файлом и номером: правка
руками.

На машине (#557) — канон: `~/.agents/elves/` и симлинки `~/.claude/rules/elves*.md`, скиллы в
`~/.agents/skills` и `~/.claude/skills`, хук. Тонкий проект (эпик #554) копии не держит, и канон его агент берёт с
машины. Для Claude Code годятся только правила `~/.claude/rules`: они грузятся без диалога внешних импортов и во всех
проектах машины, а `@~/`-импорт из CLAUDE.md проекта в сессиях приложения не грузится — одобрение нужно на каждый
worktree (#552). Другие агенты получают канон глобальным файлом правил — `~/.codex/AGENTS.md`, `~/.gemini/GEMINI.md`,
`~/.copilot/copilot-instructions.md`, `~/.config/opencode/AGENTS.md`, `~/.config/amp/AGENTS.md` — симлинком на канон,
если агент на машине есть; чужой файл с правилами пользователя установка не трогает и называет, где канон. Так было
до #180: он убрал правила с машины только из-за второй копии в проекте, а в тонком проекте её нет. Проект, где копия
ещё лежит, на время переезда грузит канон дважды — это допущено (вопрос задачи #557), хук называет двойную загрузку и
задачу проекта, чей `update` переводит его на тонкий проект (capability `update`). Флаг «правила на машину — по
желанию» отвергнут: проектов с копией единицы, а тонкий проект без канона машины остался бы без правил.

Облако ставит флоу setup script окружения claude.ai: `npm i -g @miroshnik/elves && elves install -g` — до запуска
Claude Code, под root в свежем HOME, без терминала, с `CLAUDE_CODE_REMOTE=true` (#555). `~/.claude` там может ещё не
быть, поэтому облако — тоже Claude Code: канон и скиллы видны с первого хода, личные скиллы закрывают одноимённые
скиллы проекта. Хука там нет: `~/.claude/settings.json` облако не читает (#552).

Клон Elves с `--link` даёт машине канон симлинком на себя — правка видна сразу. В самом клоне канон поэтому не должен
грузиться вторично: закоммиченного симлинка в `.claude/rules` у клона нет, а `.claude/CLAUDE.md` выключает чтение
корневого `AGENTS.md`, которое Claude Code делает сам, когда CLAUDE.md нет.

Вести ли задачу целиком без спроса — отвечать на её вопросы по рекомендации, коммитить, пушить, чинить CI и мержить
свой PR по зелёным чекам — решение проекта, а не флоу: `install` спрашивает об этом в терминале и хранит ответ в
`.agents/elves.json` (`auto`) — его видят облачная сессия и любой агент. По умолчанию «нет»: молчание не даёт
права на необратимое. В клон Elves флоу не ставится — канон в его корне; `install` пишет в нём только эту
настройку и язык.

Флоу написан по-английски — репозиторий публичный, — а агент работает с человеком на языке проекта: диалог, задачи,
промпты субагентам, документы, названия тестов спеки. Язык — тоже настройка проекта: `install` спрашивает его в
терминале или берёт из `--lang <код>` (BCP 47) и хранит в `.agents/elves.json` (`language`), `check` и хук
называют его в начале сессии. Новая установка без флага — `en`, язык флоу. У установки прошлой версии поля нет, а
флоу до него работал только по-русски — её язык `ru`, и `update` его записывает: обновление не меняет проекту язык.
Отвергнуто: копия канона на каждом языке — копии разошлись бы, а модель читает английские правила и работает на любом
языке; язык из локали машины — у агента без терминала она случайна.

Файлы флоу коммитятся, поэтому установка следит, чтобы git проекта их не игнорировал: без шима в коммите скрипт
`package.json` в CI и чужом чекауте падает на `. .agents/slot.sh`, без манифеста облачная сессия не знает режима и языка
(#558, вопрос 4). Исключения пишутся блоком Elves в конце `.gitignore` — отрицание действует, только если идёт после
игнорирующего правила; каталог снимается цепочкой `!/.agents/`, `/.agents/*`, … ровно с файлов флоу, прочее в нём
игнорируется, как раньше. Каталог, исключённый личным правилом (core.excludesFile), — `❌` без исключения:
`/.agents/*` в проекте спрятал бы прочее в нём у всех. Шаблоны, которые прятали файлы копии (`CLAUDE.md`, `.claude/`,
`vendor/`), тонкому проекту безразличны — блок копии переезд убирает.

Проверки проекта — скрипты `package.json` `lint`, `typecheck`, `test` и `test:*` — установка оборачивает в
очередь машины `slot` (capability `slot`): их зовёт любой — агент, человек в терминале, `github pr premerge`, — и все
встают в одну очередь. Обёртка — `. .agents/slot.sh && <команда>`: шим — `slot.sh` скилла вокруг `elves slot --for $$`
пакета проекта, в `if command -v elves`. Скрипт `package.json` видит `node_modules/.bin` проекта — очередь его версии;
без `elves` на PATH (CI до установки зависимостей, чекаут без пакета) команда идёт как есть, сбой `elves` роняет
скрипт его кодом — проверено в #552. Обёртки прошлых установок — `slot.sh` копии, команда строкой у `slot.ts` копии
через `bun` или `node` — `update` переписывает. `build` не
оборачивается — его запускают хостинг и Docker, где шима или пакета может не быть; watch — долгий, занял бы слот
надолго. Обёртку, снятую руками, `check` называет несоответствием, `update` возвращает; `package.json` уходит в
коммит вместе с файлами флоу.

Обёрнутый скрипт, который зовёт turbo, теряет переменные очереди: turbo 2 в strict env mode пропускает задачам только
названные в `turbo.json`, и раннер без `ELVES_SLOT_CPUS` берёт машину целиком, а вложенный скрипт в `slot` без
`ELVES_SLOT` ждёт собственный слот. `install` и `check` предупреждают готовой строкой `globalPassThroughEnv` — она в
хэш кэша не входит, а `ELVES_SLOT` у каждого прогона свой. `turbo.json`, который пропускает их только под прежними
именами флоу (`AI_DEV_SLOT`, `AI_DEV_SLOT_CPUS`, #545), работает — `slot` пока экспортирует и их, — но конфиг раннера
на новом имени их не получит: строка та же, она добавляет новые имена и оставляет прежние. `turbo.json` не правят: его ведёт проект и в нём бывают
комментарии; в `check` это строка `!`, не отставание — `update` её не исправит.

Мерж без ревью человека приложение Claude Code отклоняет и при `auto`: его разрешает правило `Bash(gh pr merge *)`
в настройках разрешений машины, а оно действует на все её репозитории — шире проекта. Такое разрешение владелец
ставит своей рукой: `install` с auto правило называет, настройки машины не меняет — иначе о нём узнают из отказа в
конце первой задачи.

Агент ставит флоу на машину из своей песочницы, а она пускает не всюду: Seatbelt у Claude Code защищает
`.claude/skills`, и установка обрывается на симлинках, когда копии в `~/.agents/skills` уже легли. Порядок поэтому такой, чтобы
повтор довёл установку: выбывшие скиллы уходят, пока их ещё перечисляет старый манифест, а новый пишется до копий —
повтор признаёт их своими, а не чужими каталогами с именем скилла. Симлинк, который уже ведёт куда надо, не
пересоздаётся: иначе `update` в песочнице падал бы на каждом запуске, даже без нового скилла. Отказ в записи — код 2 и
строка с путём и той же командой для своего терминала, а не стек. Отвергнуто: признавать своими копии, совпадающие с
файлами релиза, — это помогло бы только повтору тем же релизом и не помогло бы при обрыве посреди копии.

Пакет называется `@miroshnik/elves` — так он публикуется в npm (#556; `elves` на npm занято), репозиторий — `elves`;
прежние имена пакета — `elves` и до переименования флоу (#544) — `ai-dev`. Клон или ветка, ещё не получившие новое
имя, — тот же клон Elves: установщик узнаёт клон по всем трём именам пакета, иначе `check` в такой ветке звал бы клон
отставшим, а `install` ставил бы в него флоу. Пакет под scope bun кладёт в `node_modules/@miroshnik/elves`, и SHA
установки по спецификатору установщик ищет под полным именем: иначе пакет релиза счёл бы себя пускателем из `main` и
перезапускался бы снова.

Пакет из npm (`npm i -g`, `bun add -g`, devDependencies проекта) — сам релиз: его версия `ГГГГ.ММДД.N` — тег
`vГГГГ.ММ.ДД.N`, а коммит `elves pack` пишет в `gitHead` его package.json. SHA в спецификаторе у него нет, и без этого
установщик счёл бы себя пускателем из `main` и перезапустился бы через `bunx github:` — в облачной сессии это 403, а в
setup script установка шла бы из архива GitHub, а не из npm. Поэтому `install` из пакета npm ставит релиз своей
версии без сети.
