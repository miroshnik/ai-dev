Скилл `slot`: тяжёлые прогоны машины — проверки проекта `lint`, `typecheck`, `test` — идут очередью: одновременно
два, вместе — половина ядер, остальные ждут по порядку прихода и видят, кого ждут.

Параллельные сессии агентов — при раздаче эпика их до двадцати в одном проекте — гоняют полную проверку разом, а
каждый раннер рассчитан на всю машину. По транскриптам за две недели: пик — 23 тяжёлых прогона одновременно, 33
прогона оборвал 10-минутный таймаут инструмента, тот же набор тестов шёл 5 с в одиночку и 35 с при десятке соседей.
Правило «под нагрузкой — перезапуск после соседей» неисполнимо: узнать, когда соседи закончат, нечем, и сессии
повторяли прогон, добавляя нагрузку. Очередь даёт то, чего не было: прогон стартует, когда есть место, и выходит
таким же быстрым, как в одиночку.

Два слота по четверти ядер, а не один на половину: `lint` и `typecheck` обычно однопоточны, и два прогона по
четверти проходят очередь быстрее одного на половину. Сколько воркеров взять, раннер узнаёт из
`ELVES_SLOT_CPUS`; вторая половина машины — человеку, приложению и самим агентам.

Слот — файл-билет в `slots/` каталога личной конфигурации с PID процесса в имени. Процесс умер, даже убитый без
уборки, — его билет не в счёт и убирается первым, кто его увидит: замков, которые надо снимать руками, нет.

Песочница агента каталог конфигурации на запись не открывает, а проверки в ней идут без отключения песочницы — иначе
каждая просит разрешения. Билет тогда — в `elves/slots` временного каталога: в песочнице Claude Code он общий для
всех сессий пользователя. Очередь читается из всех мест сразу, включая временный каталог Claude Code
(`CLAUDE_TMPDIR` — он есть и вне песочницы): прогоны в песочнице и вне её (`github pr premerge`, команда с
отключённой песочницей) ждут друг друга. Терминал человека этот каталог не знает и прогоны песочницы не видит —
человек запускает тяжёлое редко. Места для билета нет нигде — одна строка предупреждения и команда без очереди:
проверка без очереди лучше, чем никакой. Отвергнуто: расширять песочницу из установщика (запись в
`~/.config/elves`) — граница песочницы решается владельцем, а не скриптом.

Без очереди — в CI, где машина отдана прогону, и внутри слота: скрипт, который зовёт другой скрипт из очереди,
иначе ждал бы сам себя. Аргументы дописываются в конец команды, как у `npm run`, — обёрнутый скрипт принимает
путь к файлу теста так же, как без обёртки.

Скрипт `package.json` не отдаёт команду slot строкой: `. .agents/slot.sh && <команда>`. Shell скрипта подключает шим
`.agents/slot.sh`, который ставит установка флоу, а шим зовёт `elves slot --for $$` пакета `@miroshnik/elves` из
devDependencies проекта (`node_modules/.bin` на PATH скрипта дают `npm run` и `bun run`): слот берётся на этот shell —
билет с его PID, слот держится, пока shell не вышел, — и shell экспортирует переменные очереди. Версия очереди —
версия пакета проекта, как у харнесса и spec-скриптов. Без `elves` на PATH (CI до установки зависимостей, чекаут без
пакета) команда идёт как есть, сбой `elves` роняет скрипт его кодом, и команда не идёт. Механизм один — шим: своего
`slot.sh` у скилла нет, и спека проверяет ту обёртку, которую ставит установщик (#585). Команда остаётся обычной
командой скрипта, и инструменты, которые разбирают скрипты `package.json`, её видят: knip по `bun test` берёт входами
файлы тестов и `preload` из `bunfig.toml`, а бинарник команды считает использованной зависимостью. Команду строкой
knip не видел: deadCode проекта краснел от установки флоу, а не от кода, и проект глушил его записями `entry` и
`ignore`. Отвергнуто: команда без кавычек после `slot.ts` — knip отбрасывает всё, что идёт после файла скрипта `bun`;
префикс `ELVES_SLOT_CPUS=$(…) <команда>` — переменная доходит только до первой простой команды (`tsc && eslint .`);
второй скрипт с исходной командой — удваивает скрипты проекта; записи в конфиге knip проекта — то, от чего и уходим.
Исключение — Yarn 2+: он выполняет скрипты своим shell без `.`, `eval` и `export`, шим там не подключить, и команда
остаётся строкой у slot пакета — проверки в очереди, knip её не видит. Пакет там — через bunx версии проекта:
`bunx @miroshnik/elves@"$(jq -r '.devDependencies["@miroshnik/elves"]' package.json)" slot '<команда>'`. Голый
`elves slot` (до #608) Yarn 2+ запускал Node-ом, мимо шебанга, при любом `nodeLinker`: Node не снимает типы у bin
`.ts` под `node_modules`, а с PnP `node_modules` нет вовсе, — проверки проекта падали. bunx идёт мимо Yarn и находит
пакет без `node_modules`; нужны `jq` и подстановка `$(…)` — shell Yarn её умеет (проверено на Yarn 4.9.1, оба
`nodeLinker`). Отвергнуто: `nodeLinker: node-modules` условием флоу — меняет раскладку зависимостей проекта и не
лечит запуск `.ts` Node-ом.

Прямой вызов — `bun --no-env-file slot.ts '<команда>'`: Bun сам подгружает env-файлы рабочего каталога (`.env`,
`.env.local`), а slot передаёт своё окружение команде — прод-ключи из `vercel env pull` дошли бы до раннера тестов,
который без обёртки их не видел: тесты «ключ не задан» краснели локально и были зелёными на CI. С флагом команда
получает то же окружение, что и без обёртки; раннер, который подгружает env-файлы сам (`bun test`), подгружает их
как прежде. Команда скрипта через slot не идёт вовсе: у неё окружение скрипта и две переменные очереди — `elves slot
--for` их только печатает. `elves slot '<команда>'` пакета — прямой вызов из `node_modules/.bin` и обёртка Yarn 2+
через bunx — идёт через шебанг bin: `sh` запускает Bun с `--no-env-file` (#592, #608). Отвергнуто: `env = false` в `bunfig.toml` проекта — отключил бы env-файлы и собственным
`bun test`, `bun run dev` Bun-проекта (tests/standards/no-env-file).

Отвергнуто: хук Claude Code, переписывающий команды, — ловит только Claude и держится на регулярках, а скрипт
`package.json` зовут все, включая человека в терминале; правило без механизма — его уже не исполняли; лимит
сессий — думать и править код дёшево, мешают только тяжёлые прогоны; пониженный приоритет (`nice`) — интерфейсу
легче, но прогоны всё равно душат друг друга и упираются в таймауты.

Флоу переименован (`ai-dev` → `elves`, #545), а проекты переходят по одному: копия проекта, которую `update` ещё не
принёс, зовёт slot прошлого релиза, конфиги раннеров читают `AI_DEV_SLOT_CPUS`, `turbo.json` пропускает `AI_DEV_SLOT`.
Поэтому slot экспортирует переменные под обоими именами с одними значениями, вложенный вызов узнаёт по любому из них,
а очередь читает и билеты прежнего slot в `ai-dev/slots` временного каталога: иначе прогоны проектов до и после
`update` не ждали бы друг друга, а вложенный скрипт прошлого релиза ждал бы собственный слот. Каталог личной
конфигурации у старого и нового slot один: до `update -g` новый читает `~/.config/ai-dev`, после — старое имя
ведёт симлинком в `~/.config/elves` (capability `update`).
