# ci-wait

Скилл `ci-wait`: агент дожидается исхода всех чеков PR или коммита одним скриптом — PASS, FAIL, TIMEOUT или
ERROR, — а не угадывает по первому ответу GitHub, что CI прошёл.

Сразу после push чеков ещё нет, и «пусто» легко принять за «прошли»; поздний чек регистрируется, когда первые
уже зелёные. Поэтому пустой список — ожидание, а финал засчитывается, только когда снимок без pending
повторился два опроса подряд.

У коммита (прогон на `main` после мержа, деплой) чеки лежат в двух местах: commit statuses пишут внешние
сервисы и хостинги, check-runs — GitHub Actions. Ожидание по одним статусам висело до таймаута на коммите, где
весь CI — Actions, поэтому `status <sha>` ждёт оба вида, а `--context` ищет чек по имени в обоих.

Отвергнуто: `gh run watch` видит только Actions и не видит статусы хостинга; `gh pr checks` не принимает SHA;
`sleep` в цикле без исходов не отличает «не зарегистрирован» от «прошёл».

## Коммит ждут до исхода всех его чеков — и статусов, и check-runs GitHub Actions

<details><summary>✅ 7 тестов</summary>

- ✅ на коммите только check-runs Actions — PASS, когда все завершились успешно
- ✅ statuses и check-runs вместе — PASS, только когда pending нет ни там, ни там
- ✅ чеков на коммите ещё нет — ожидание, а не PASS
- ✅ упавший check-run — FAIL с его именем
- ✅ поздно зарегистрированный чек не проскакивает: финал — два опроса подряд без pending
- ✅ --context находит чек по имени среди check-runs
- ✅ чеки не завершились к сроку — TIMEOUT

</details>
