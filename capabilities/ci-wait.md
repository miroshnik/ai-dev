# ci-wait

Скилл `ci-wait`: агент дожидается исхода всех чеков PR или коммита одним скриптом — PASS, FAIL, TIMEOUT или
ERROR, — а не угадывает по первому ответу GitHub, что CI прошёл.

Сразу после push чеков ещё нет, и «пусто» легко принять за «прошли»; поздний чек регистрируется, когда первые
уже зелёные. Поэтому пустой список — ожидание, а PASS засчитывается, только когда снимок без pending
повторился два опроса подряд.

У коммита (прогон на `main` после мержа, деплой) чеки лежат в двух местах: commit statuses пишут внешние
сервисы и хостинги, check-runs — GitHub Actions. Ожидание по одним статусам висело до таймаута на коммите, где
весь CI — Actions, поэтому `status <sha>` ждёт оба вида, а `--context` ищет чек по имени в обоих. `pr <N>`
ждёт так же — по SHA головы PR, перечитывая её каждый опрос.

`merged <N>` ждёт чеки коммита мержа PR, беря его SHA из PR (#285): после мержа SHA добывали отдельными ходами
`gh pr view` на пиковом контексте сессии — замер показал их в 10 закрытиях из 17. С номером PR ожидание
запускается тем же ходом, что `github task actualize`. Невлитый PR — ERROR сразу: ждать нечего.

Одноимённые check-runs коммита сводятся к последнему (#319): на одном SHA лежат check-runs всех прогонов — прогон,
отменённый новым push, остаётся и после того, как голову вернули на прежний коммит (проверка поломкой), — и
отменённый ранний давал ложный FAIL при зелёном последнем. Итог — за check-run с наибольшим `id` у пары «имя,
приложение», как у обязательных чеков GitHub; одноимённые чеки разных приложений — разные чеки. Статусы API
сводит к последнему на контекст сам.

Упавший чек завершает ожидание сразу (#246): рядом с ним бывает долгий превью-деплой, и сессия узнавала о
красном CI на десятки минут позже, а монитор CI приложения без Auto-fix её не будит. Полный снимок — флагом
`--wait-all`.

PR с конфликтом с базой — ERROR, не дожидаясь чеков: GitHub не создаёт merge-ref, workflow на `pull_request` не
запускаются, и ожидание кончалось итогом по одним статусам хостинга — с прошедшим деплоем это был бы PASS без
единого прогона CI. По той же причине обязательные чеки базовой ветки (ruleset и классическая защита) ждутся по
именам: незарегистрированный обязательный — не финал.

Конфликт — только подтверждённый повторным опросом той же головы (#472): сразу после `git push --force-with-lease`
GitHub ещё отдаёт `mergeable: false` прежней головы — её конфликт с `main` и был причиной ребейза, — и ожидание
кончалось ERROR, хотя у новой головы конфликта нет и CI на ней уже идёт (дважды подряд в одном PR). Первый опрос с
`false` — ожидание с пунктом `conflict with base <база>: rechecking`; второй опрос той же головы с `false` — ERROR;
`false` прежней головы конфликт новой не подтверждает. Цена — настоящий конфликт выходит через один интервал опроса,
а не на первом. Отвергнуто: судить по прогону CI на голове (есть прогон `pull_request` — merge-ref построен) — не
работает в репозитории без Actions; по времени push — лишние запросы, а дата коммита — не время push.

Прогон Actions, не ставший чеком, — не PASS (#356): PR правил `ci.yml`, файл перестал разбираться, и GitHub не создал
ни одного check-run — только прогон-«пустышку» на голове (имя — путь файла, событие `push`, без job). Ожидание видело
одни чеки хостинга и отдало PASS; по канону дальше — мерж PR без единого прогона тестов. Обязательные чеки этого не
ловят, когда их нет или правила не прочитать (приватный репозиторий на Free). Поэтому чеки коммита дополняют прогоны
Actions на SHA: упавший без job (не разобран — имя прогона равно пути; не стартовал — в его check suite нет check-runs)
— FAIL с путём файла и ссылкой. А `pr` ждёт прогон каждого активного workflow, который по своему `on:` на SHA головы
срабатывает на PR: у PR из форка нет и «пустышки», и тот же запрет на PASS даёт TIMEOUT с путём workflow. Ждётся
только то, что решается без диффа PR: `pull_request` без фильтров или с ветками, пускающими базовую; фильтр путей,
`types` без `synchronize`, отрицание в ветках — не ждём, ложный TIMEOUT. Файл, который не разбирается, — ждём.

Прогон Actions в очереди — тоже не PASS (#360): прогон CI на голове PR стоял `queued`, check-runs у него ещё не было.
Прогон на SHA есть — workflow не «без прогона»; не упал — не FAIL; и итог снова сводился к чекам хостинга (превью и его
комментарий) — PASS, мерж без CI. Поэтому незавершённый прогон без check-runs в своём check suite — pending с путём
файла (`workflow queued: <путь>`), пока раннер не возьмёт его и не появятся чеки job.

Публикация спеки — не проверка (#443): job `spec-publish` выкладывает документацию в ветку `spec` и ничего не
проверяет — за три недели в проектах ни одной находки, а его гонка пуша давала FAIL ожидания после мержа при зелёных
тестах и деплое. Поэтому check-run `spec-publish` (и `<job> / spec-publish` — тот же job в реюзабельном workflow) не
ждётся и не даёт FAIL ни в одном режиме; названный в `--context` — ждётся, как любой чек. Имена — те же, что у
`github pr premerge`: его красный — не красный `main`; обе копии правила держит одна таблица (стандарт
`spec-publish-job`).

Только REST: `gh pr checks` ходит в GraphQL, его квота общая на все параллельные сессии пользователя и
кончалась, давая ERROR при нормально идущих чеках. Лимит REST — ожидание до сброса квоты, а не ERROR.

Видно, чего ждём (#432): ожидание CI — главный расход времени сессии (медиана 25 мин на сессию в одном проекте, 86 —
в другом), а владелец не понимал, чего ждём. Пульс в stderr на каждый опрос и строка `CHECK` на каждый чек давали в
выходном файле простыню; агент читал его до уведомления (259 раз, из них 125 — циклы `sleep`/`until`) и после — ради
строки `RESULT` (~330 раз), хотя код выхода уже исход. Теперь строка состояния — только при его смене: время, сколько
прошло от начала, сколько чеков завершено и чего ждём — pending, незарегистрированные обязательные, workflow без прогона
(до пяти имён); TIMEOUT называет то же полностью. В SKILL.md первой фразой разбора итога: итог — код выхода, файл не
читать.

Интервал опроса растёт с длиной ожидания — десятая доля прошедшего, до 5 минут: долгий деплой опрашивается в разы
реже, квота REST, общая для параллельных сессий, не кончается, а итог приходит не позже чем через десятую долю
ожидания. Подтверждающий опрос перед PASS — с начальным интервалом: всё уже завершилось, выросший только задержал бы
итог. Ожидание сброса квоты не съедает `--timeout` (всего до часа — одно окно квоты): сброс бывает через 40 минут при
таймауте 30, и вместо ERROR выходил TIMEOUT без единого опроса после сброса. 49 `RESULT: ERROR … rate limit` в разборе
сессий — GraphQL-квота `gh pr checks` до перехода на REST; лимит REST ожидание уже переживало.

Сбой `gh` — не исход (#330), и в запросах до первого опроса: проверку коммита у `status` делал один запрос
без повтора, и во время инцидента GitHub разовый сбой давал «коммит не найден», код 3, при существующем коммите —
сессия читала ERROR как неверный вызов. «Не найден» — только ответ API «нет» (422 «No commit found», 404), иной
сбой — повтор, как в опросе, ERROR — после пяти подряд. Так же обязательные чеки базовой ветки: «нет» — только
403 (нет прав читать правила) и 404, разовый сбой больше не стирает их до конца ожидания.

`issue <N>` ждёт закрытия issue (#282): красный `main` чинит одна сессия по багу «`main` красный…» (`github pr
premerge`, код 3), остальные ждут его закрытия — фоновой командой, чьё завершение будит сессию, а не опросом
руками. Закрытый issue — PASS сразу: повторный опрос нужен поздно регистрирующимся чекам, а не issue.

Отвергнуто: `gh run watch` видит только Actions и не видит статусы хостинга; `gh pr checks` не принимает SHA и
тратит квоту GraphQL; `sleep` в цикле без исходов не отличает «не зарегистрирован» от «прошёл»; число
ожидаемых чеков из прошлого прогона ветки — набор чеков законно меняется (фильтры путей workflow), счёт по
прошлому прогону давал бы ложный TIMEOUT; по той же причине ожидаемые workflow — из `on:` файлов на SHA, а не из
прогонов на прошлых PR (#356): workflow с фильтром путей шёл на всех недавних PR, а на PR с одними доками не пойдёт.
