# github-task

Скилл `github`, `task new`, `task status`, `task close` и `task drop`: задачу заводят, двигают по доске,
закрывают после мержа и снимают одной командой, и она всё время по канону `AGENTS.md`.

Заведённая руками задача остаётся без статуса, приоритета или связи с эпиком — и выпадает с доски и из оценки
эпика. Команда ставит всё сразу: тип или метку, проект и `Бэклог`, `Priority`, эпик, blocked by, milestone, а
проверяет всё до создания — задача не появляется наполовину. Статус подзадачи тянет за собой эпик, закрытая без
выполнения уходит из проекта.

Сессия ведёт одну задачу: `task status "В работе"` закрепляет первую за сессией и отказывает другой. Правило «Сессия =
задача» прозой не держалось: за три недели 41 из 94 сессий с работой вели больше одной задачи (в 31 вторую назвал сам
пользователь), и в 19 из 36 многозадачных привязка факта `est` по названию сессии ломалась. «В работе» зовёт каждая
сессия — это точка для механизма: на той же истории отказ второй задаче останавливает 20 из 20 многозадачных сессий и
не даёт ложных отказов в 83 остальных. Ключ закрепления — id сессии (`CLAUDE_CODE_SESSION_ID`), а не чекаут: worktree сессии
переиспользуют, ключ «чекаут» дал бы 42 ложных отказа. Задача, заведённая в сессии с закреплённой, остаётся в «Бэклог»:
`task new` называет её первый промпт для новой сессии.

## task status берёт в работу одну задачу на сессию

Сессия ведёт одну задачу: по сессии `est` считает факт, а вторая задача в той же сессии отдаёт своё время первой.
Правило прозой не держалось, поэтому первая задача «В работе» закрепляется за сессией файлом
`<каталог конфигурации>/sessions/<CLAUDE_CODE_SESSION_ID>`, другой задаче скрипт отказывает до изменений. Закрепление
не снимает ни одна команда: ошибочное убирает человек, удалив файл.

<details><summary>✅ 11 тестов</summary>

- ✅ первая задача «В работе» закрепляется за сессией — файл sessions/\<id сессии> в каталоге конфигурации называет owner/repo#N
- ✅ другая задача «В работе» в той же сессии — отказ (код 2) до изменений: закреплённая задача, первый промпт новой сессии и файл закрепления — одной строкой
- ✅ та же задача «В работе» повторно — без отказа
- ✅ задача с тем же номером в другом репозитории — другая задача: отказ
- ✅ эпик не закрепляется — после него сессия берёт подзадачу
- ✅ «Бэклог» и «Готово» другой задаче — без отказа: закрепляет только «В работе»
- ✅ закрепление не снимают ни «Готово», ни task close — другая задача после них всё равно отказ
- ✅ другая сессия с тем же каталогом конфигурации берёт другую задачу без отказа

## Статус ставится, даже если проект ещё не показал задачу

GitHub добавляет задачу в проект не мгновенно для чтения: ответ createIssue и чтение задачи могут ещё не показывать
элемент, а повторное добавление отвечает «Content already exists». Статус всё равно ставится — по элементу, который
станет виден после короткой паузы.

<details><summary>✅ 3 теста</summary>

- ✅ createIssue ещё не показывает элемент, добавление — «уже есть»: task new всё равно ставит Бэклог
- ✅ задачу проект уже добавил, а чтение её ещё не показывает: task status перечитывает с паузой и ставит статус
- ✅ элемент так и не виден — понятная ошибка с тем, что повторить, а не падение

</details>

## task close закрывает задачу одной командой

После мержа PR сессия делала ещё ≈21 ход на пиковом контексте — факт, статус, milestone, уборка ветки. `task close`
сворачивает это в один вызов; актуализацию блока делает субагент со свежим контекстом.

<details><summary>✅ 17 тестов</summary>

- ✅ PR задачи влит: задача закрыта, факт записан est, Status «Готово» — в выводе всё сделанное и следующий шаг
- ✅ последняя строка вывода называет три исхода конца сессии: всё сделано, всё сделано, но есть вопросы, осталось
  > Параллельных сессий много, и по хвосту каждой надо видеть, закончила она или чего-то ждёт. Подсказка приходит с
  > выводом `task close`: сессия на пиковом контексте, и канон от неё дальше всего. Исходов три: работа сделана, а
  > владельцу есть что решать — «Сессию можно закрывать» читалось бы как «решать нечего», и вопросы терялись.
- ✅ последняя строка вывода называет архивацию сессии в режиме auto — только после «Всё сделано. Сессию можно закрывать.»

  > строки «Всё сделано. Сессию можно закрывать.» сессия архивирует себя сама. Архивная сессия уходит из списка, и
  > вопросы в её последнем ответе владелец уже не прочтёт — после двух других строк архивации нет. Манифест команда
  > не читает — называет условие словами.
- ✅ последняя строка вывода не считает вопросом информацию без решения: строка и архивация — как у «всё сделано»
  > «Есть вопросы» без вопроса — шум: наблюдение, срок, предупреждение владелец читает в отчёте, решать ему нечего.
  > Такая сессия заканчивает как обычно и в режиме auto архивирует себя.

  > задачи тогда — среди последних PR основной ветки: по ветке `<type>/<N>-<slug>` или «Closes #N» в теле.
- ✅ связи нет, влитый PR с «Closes #N» в теле — задача закрыта по нему
- ✅ связи нет и влитого PR задачи нет — отказ с перечнем проверенного

## task close убирает влитое

Влитое убирается по правилу «влитое удаляю целиком» (скилл github, «Git, PR и мерж — механика»): чекаут — на origin/main, ветка — долой локально и на хостинге.

<details><summary>✅ 4 теста</summary>

- ✅ чекаут на ветке задачи, PR влит: после close — detach на origin/main, локальной и удалённой ветки нет
- ✅ связи PR с задачей нет, влитый PR найден по ветке — ветка убрана
- ✅ ветка не влита — не тронута, строка ○
- ✅ текущий каталог — не чекаут репозитория задачи: ветки не трогаются

</details>
