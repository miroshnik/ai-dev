# task-env

Скилл `task-env`: у задачи #N свой стек Docker Compose — проект Compose `<проект>-<N>` (эпик #392), — у приложений
задачи свои адреса `<сервис>.<N>.<проект>.localhost` — их раздаёт один на машину прокси Traefik по меткам контейнеров,
а `check -g` говорит, работает ли он; `check` проекта держит compose-файл правил изоляции стеков задач; `task-env up`,
`e2e` и `down` поднимают, пересоздают для прогона и снимают стеки задачи по её номеру, а compose-файл получает адреса
стека в `TASK_ENV_<СЕРВИС>_URL`; `task close` снимает стеки сам, а `prune` находит и снимает стеки закрытых задач.

Параллельные сессии одного проекта держат свои приложения одновременно. На `localhost` с разными портами они делят
куки — куки портов не различают, — и браузер агента и браузер владельца разлогинивают друг друга; свободный порт ещё
и ищут перебором. Разные хосты — разные куки: `*.localhost` резолвится в loopback и в браузере — безопасный
контекст. Приложения задачи живут в контейнерах её стека Compose (эпик #392), поэтому хосты раздаёт прокси, который
видит контейнеры, — Traefik с провайдером Docker: маршрут появляется, когда контейнер стартует, и пропадает, когда
он останавливается, без перезагрузки и без портов на хосте. Отвергнуто: portless — запускает процессы на хосте и к
контейнерам не подходит; порт от номера задачи — куки всё равно общие.

## Почему прокси такой

- **Один на машину**, проект Compose `elves-proxy` из `skills/task-env/proxy/compose.yaml`, `restart:
  unless-stopped` — поднимается вместе с Docker; `task-env proxy up` приводит его к compose-файлу скилла и ждёт
  healthcheck.
- **Публикует только помеченное** (`exposedByDefault: false`): база или очередь стека в сети прокси не становится
  адресом сама; маршрут даёт override стека задачи (#393) только HTTP-сервисам. Метки строит `proxyLabels`
  скрипта: роутер `<стек>-<сервис>` по `Host(...)` на точке входа `web`, сервис — на порт внутри контейнера, сеть,
  через которую прокси ходит к контейнеру, — меткой `traefik.docker.network` (#545, ниже «Переход с `ai-dev-proxy`»).
- **HTTP на 80 и только на `127.0.0.1`**: адрес без порта, а приложения задач не видны в локальной сети. HTTPS — когда
  понадобится проекту (эпик, вопрос 11): cookie `Secure` на `http://*.localhost` Chromium принимает и так.
- **Имя и порт — из `ELVES_PROXY` и `ELVES_PROXY_PORT`**: тест поднимает свой прокси рядом с рабочим, не трогая
  его, занятый порт 80 — тот же выход. Значения по умолчанию — только в скрипте (`proxyName`, `proxyPort`): он
  передаёт их compose-файлу явно — и сеть провайдера по умолчанию `ELVES_PROXY_DEFAULT_NETWORK`, — а в файле —
  `${…:?}` без своих значений (#396, вопрос 1): два значения по умолчанию без сверки разошлись бы молча, а дашборд
  строит ссылки по порту скрипта. `check -g` установщика импортирует `proxyName`; тест сверяет, что `check -g` ищет
  проект с именем скрипта.
- **API — для дашборда**, по хосту `<имя прокси>.localhost` на точке входа `web`, без UI Traefik (#396, вопрос 3):
  дашборд видит адреса задачи по маршрутам через loopback — доступ к Docker, а это вся машина, ему не нужен, и ответ
  одинаков в песочнице и вне её. Не отдельный порт
  `:8080` — ещё настройка и ещё конфликт; сайт, навёдший своё имя на `127.0.0.1`, приходит со своим `Host` и получает
  404. Роутер назван по имени прокси: тестовый прокси видит метки рабочего, а роутеры одного имени с разными
  правилами Traefik отбросил бы.
- **Адрес задачи разбирается в скрипте** (`taskAddress`, `hostProject`, `addressUrl`): схему адреса знает один
  модуль — и тот, кто поднимает стек (#393), и дашборд.

## Переход с `ai-dev-proxy` — один релиз в обеих сетях

Переименование флоу (ai-dev → Elves, эпик #542) переименовало прокси: проект Compose и сеть `ai-dev-proxy` →
`elves-proxy`, переменные `AI_DEV_PROXY*` → `ELVES_PROXY*`, настройки проекта `.agents/ai-dev.json` →
`.agents/elves.json`. На машине в это время работают прокси под прежним именем и стеки задач других проектов в его сети;
compose-файл проекта мог назвать сеть `ai-dev-proxy` руками — так было в примере `reference.md`. Решение владельца
(#545, вариант «а»): прокси один релиз в обеих сетях, `check` называет прежнюю сеть в compose-файле с правкой, проекты
переходят своей задачей — ничего не падает.

- **`proxy up` занимает место прежнего прокси** (`FORMER_PROXY`; `up` стека зовёт его сам, когда прокси не
  запущен): контейнер прежнего держит порт — он удаляется; сеть остаётся — в ней стеки, поднятые до переименования, —
  и новый прокси входит в неё override на stdin Compose, как стек задачи: сети на машине может не быть, в файле ей не
  место. Нет сети прежнего прокси — прокси только в своей, чужую сеть он не создаёт. Новый контейнер создаётся
  (образ скачан) до удаления прежнего: не скачался образ — прежний прокси продолжает работать. Альтернатива — оставить
  прежний прокси на месте и поднять новый рядом — упирается в порт: адрес без порта есть только у одного.
- **Сеть, через которую прокси ходит к контейнеру, — детерминированная.** Провайдер docker Traefik берёт сеть из метки
  `traefik.docker.network`, без неё — `providers.docker.network`; когда этой сети нет среди сетей контейнера, он берёт
  «первую доступную» — первую при обходе map Go, а порядок обхода случайный при каждой сборке конфигурации. Стек до
  переименования — в `<стек>_default` и `ai-dev-proxy`, новый — в `<стек>_default` и `elves-proxy`: с одной сетью
  провайдера для обоих один из стеков отвечал бы через раз. Поэтому стеку задачи сеть прокси называет метка (её
  ставит `proxyLabels`), а сеть провайдера по умолчанию — прежняя, пока прокси в ней (меток у стеков до переименования
  нет), иначе своя. Без метки и с сетью провайдера `elves-proxy` медленный тест падал на первой же пересборке маршрутов —
  проверено.
- **`check` называет сеть `ai-dev-proxy`** в compose-файле проекта своей строкой `❌` — прежнее имя прокси и правка:
  убрать сеть, `task-env up` добавляет сеть прокси HTTP-сервисам `env.http` сам. Код — как у нарушения, 1: это та же
  внешняя сеть, только правка другая. Пока проект не перешёл, сеть есть и его стек поднимается.
- **Прежние порт и настройки читаются запасными**: `ELVES_PROXY_PORT`, без неё — `AI_DEV_PROXY_PORT` (владелец задал
  её в профиле, когда порт 80 был занят); `env.http` — из `.agents/elves.json`, пока его нет (установка до `update`,
  который файл переносит) — из `.agents/ai-dev.json`, сообщение называет прочитанный файл.
- **Прежнее имя у тестового прокси — производное**: `ai-dev-proxy` — прежний только у прокси с именем по умолчанию, у
  прокси с другим именем — `<имя>-former` (`formerProxyName`). Не переменная: тест, забывший её задать, удалил бы
  контейнер прокси машины, а производное имя тестового прокси до прокси машины не доходит по построению; и настройкой
  на один релиз меньше. Тест перехода поднимает свой «прежний» прокси на явном свободном порту, как `ai-dev-proxy` на
  80: порт, который Docker выдал сам, Docker 29 второму контейнеру отдаёт молча — тот запускается без публикации, и
  конфликт порта тест бы не увидел. Кто ответил, тест сверяет по `Hostname` whoami, а не по коду 200. Имена стеков теста
  — раньше по алфавиту, чем сети прокси: порядок обхода map Go случайный, но неравномерный — чаще первой идёт сеть,
  первая по алфавиту, — и без выбора сети стек теста почти всегда уходит в чужую сеть, а не проходит случайно.
- **Один релиз**: следующий убирает переход — `FORMER_PROXY`, `AI_DEV_PROXY_PORT`, `.agents/ai-dev.json` и строку
  `check` о прежней сети; стеки, которые остались только в `ai-dev-proxy`, переходят повторным `up`. Прокси под прежним
  именем, оставшийся на машине, называет `check -g` установщика по `FORMER_PROXY`.

## Почему строка в `check -g`

Прокси не запущен — адреса задач молчат, и сессия ищет причину в приложении. Строка в `check -g` и в хуке
`SessionStart` называет его состояние в начале каждой сессии с командой запуска. Код `check` она не меняет:
незапущенный прокси — не отставание флоу. Имя прокси установщик берёт у скрипта скилла (`proxyName`), а `docker`
спрашивает сам: скрипт считает «docker не найден» причиной недоступности, а строке нужно молчание. Без Docker на машине строки нет: стеков задач без него нет, а строка в каждой сессии — шум;
Docker есть, но не отвечает — строка с причиной.

## Правила изоляции compose-файла

Compose разводит стеки одного проекта по имени проекта: контейнеры, тома и сеть получают его префикс. Четыре записи в
compose-файле префикс обходят и ломают изоляцию молча:

- `container_name` — у двух стеков один контейнер: второй стек не поднимется;
- фиксированный порт хоста (`5432:5432`, `127.0.0.1:5432:5432`) — второй стек не поднимется; порт, который выдаёт
  Docker (`127.0.0.1::5432`, `5432`), и сервис без `ports` — норма: снаружи — через Traefik или `docker compose port`;
- том или сеть с `name:` или `external` — общие для всех стеков: `down -v` одной задачи стирает тома другой, сеть
  сводит сервисы разных задач;
- абсолютный путь к коду в `volumes` и `build` — стек задачи монтирует и собирает чужой чекаут, а не свой worktree.

`task-env check` называет каждое нарушение строкой `❌` с правилом и сервисом (у тома и сети — с сервисами, которые их
берут), код 1; чистый compose-файл — код 0. Его зовёт `check` проекта (capability `update`): правила живут в скилле
рядом со скриптом, который поднимает стек задачи, а не копией в установщике (#398, вопрос 1).

## Почему правила читают `docker compose config`, а не YAML

Скрипт читает не сам файл, а `docker compose config --format json`: Compose уже свёл формы записи — короткую и длинную
запись портов и томов, override-файл, переменные, `extends` — к одной, а второй разбор их своими руками разошёлся бы с
Compose на краях. Три поправки к его нормализации:

- `--no-path-resolution` — иначе Compose сам делает относительные пути абсолютными, и абсолютный путь в файле от
  относительного не отличить;
- имя `<проект>_<ключ>` Compose дописывает каждому тому и сети сам — нарушение только имя, которое от него отличается,
  или `external`;
- `--profile '*'` — тяжёлые сервисы в `profiles` проверяются наравне с остальными: без профиля `config` их не
  показывает.

Абсолютный путь к ресурсу машины в `volumes` — сокет Docker, `/etc/localtime` — не код и стеки не сводит: источник из
`/var/run`, `/run`, `/etc`, `/dev`, `/proc`, `/sys` — норма (#398, вопрос 3). `~` — путь из домашнего каталога, то есть
абсолютный. В `build` любой абсолютный путь — к коду.

## Правила: не проверено — не ошибка

Демон Docker для `config` не нужен, команда идёт и в песочнице агента. Нет `docker` или его плагина `compose`, `config`
не разобрал файл (незаданная обязательная переменная) — строка `○` «not checked», код 2: о нарушениях это ничего не
говорит. Проект без compose-файла — проверка молчит, Docker не зовётся. Файл ищется под теми же именами и в том же
порядке, что у Compose: `compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml`.

## Почему стек задачи такой

- **Номер — из ветки** `<type>/<N>-slug`, разбором стандарта `task-branch` (своя копия `taskBranch`: скилл ставится
  один). Без номера — стек основного чекаута `<проект>`: у `main` и у ветки worktree до переименования своей задачи нет.
- **`<проект>` — имя репозитория `origin`, без remote — каталог основного чекаута** (#393, вопрос 6). Compose по
  умолчанию берёт каталог, а у worktree приложения он случайный: стеки одного проекта звались бы по-разному, а адреса
  было бы не угадать.
- **Override — на stdin Compose, а не файлом.** Скрипт добавляет только метки и сеть прокси HTTP-сервисам `env.http`
  (#393, вопрос 4): в compose-файле порт базы от порта приложения не отличить. Файл `compose.override.yaml` был бы
  файлом проекта, и `check` назвал бы его внешнюю сеть нарушением; с явными `-f` Compose свой override-файл проекта не
  берёт — скрипт передаёт его сам. Сети сервиса — его собственные, как их свёл Compose, плюс сеть прокси: перечисленные
  сети заменяют неявную `default`.
- **`up --build --wait`**: стек идёт на коде своего worktree, а не на образе прошлого подъёма; `--wait` возвращает,
  когда сервисы запущены и здоровы. Прокси не запущен — `up` поднимает его сам (#393, вопрос 8): он один на машину,
  отдельный шаг агента ничего не даёт.
- **e2e — свой стек с чистыми томами**, отдельно от dev: прогон не видит данных разработки и прошлого прогона и не
  портит их. Команда прогона — дочерний процесс скрипта на хосте, вне песочницы вместе с ним, адреса — в переменных
  `TASK_ENV_*` (#393, вопрос 7): префикс не задевает переменных проекта. Стек остаётся до следующего прогона — упавший
  разбирают на нём.
- **Свой адрес приложение берёт из compose-файла** (#413): `up` и `e2e` отдают процессу `docker compose` адреса
  HTTP-сервисов стека в `TASK_ENV_<СЕРВИС>_URL` — те же имена, что у команды e2e, — и compose-файл пишет `APP_URL:
  ${TASK_ENV_WEB_URL:-http://localhost:3000}`. Адрес из запроса (Traefik передаёт `Host`) фреймворку с адресом в
  настройке — базовый URL, OAuth redirect URI, ссылки в письмах — не годится. Адрес известен до подъёма: хост — по
  стеку, порт — прокси; у стека e2e — свои адреса. Только окружение процесса, без файла: `docker compose` руками и CI
  получают значение по умолчанию compose-файла, а `.env` в проекте был бы виден всем стекам чекаута.
- **`down` — по имени проекта Compose из `/`**, без compose-файла: к `task close` worktree может уже не быть, а
  найденный Compose файл скрыл бы сервисы других профилей. Снимаются оба стека задачи с томами, чужие — нет.
- **Не поднялся — сервис, состояние, вывод healthcheck и хвост лога**, код 1 (#393, вопрос 5): проверка окружения —
  первый подъём стека в задаче, а не `check` в хуке с таймаутом 60 с.
- **Подсети.** Каждый стек — своя сеть, а пулов адресов у Docker Desktop по умолчанию — около 30 сетей на машину:
  `up` объясняет отказ Docker `all predefined address pools have been fully subnetted` и ведёт к
  `default-address-pools` (`skills/task-env/SKILL.md`, «Network subnets»).

## Уборка: `down` в `task close`, `prune` — для сирот

Стек задачи живёт, пока его не снимут, — с томами и сетью, а сетей у Docker немного. Поэтому его снимает `task close`
скилла `github` (#395): `task-env down <N>` в чекауте задачи, строка на стек — `+` снят, `○` нет, `!` не снят;
ошибка снятия закрытие задачи не валит.

- **Стеки на машине — по метке `com.docker.compose.project`** у контейнеров, томов и сетей, а не по `docker compose
  ls`: стек, от которого остались одни тома (`down` без `-v`, контейнеры удалены руками), в его списке не виден, а
  `down -v -p <стек>` снимает и его (#395, вопрос 2; Compose 5.6).
- **Нет compose-файла в чекауте — Docker не зовётся**, строка `○` (#395, вопрос 4): `task close` зовёт `down` в каждом
  проекте, и проект без Compose при остановленном Docker получал бы `!` на каждом закрытии.
- **`prune` — стеки закрытых задач**, оставшиеся на машине: задачу закрыли без `task close`, закрытие не достало
  Docker, задача удалила compose-файл. Номер — из имени стека `<проект>-<N>[-e2e]`, состояние — по GitHub (`gh api`,
  репозиторий — `origin` чекаута). Закрыта — стеки снимаются с томами сразу, без вопроса: стек закрытой задачи не
  нужен никому (#395, вопрос 1). Открытая задача, основной чекаут, номер, которого нет среди задач, непроверенное
  состояние — стек остаётся.
- **Стек другого репозитория с тем же именем `prune` не трогает** (#395, вопрос 3): `<проект>` — имя репозитория, и
  основной стек репозитория `shop-2` зовётся как стек задачи #2 проекта `shop`. Каталог его контейнеров
  (`com.docker.compose.project.working_dir`) есть и это другой проект — стек чужой; каталога нет (worktree удалён) или
  контейнеров нет — свой.
- **Docker из `task close` — вне песочницы**: запись `excludedCommands` для `bun <путь>/github.ts *` вызов из песочницы
  не выводит, как и для этого скрипта (ниже, «Проверено на машине»); `task close` агент зовёт вне песочницы (скилл
  `github`).

## Проверено на машине (2026-10-13)

- Порт 80 на macOS без sudo: Docker Desktop публикует `127.0.0.1:80` от пользователя.
- Cookie `Secure`, `Secure; HttpOnly` и `__Host-` по `http://*.localhost` в Chromium Playwright (1.63, Chromium 153)
  ставятся сервером и `document.cookie` и уходят обратно, через прокси тоже.
- Песочница Claude Code адреса по умолчанию не достаёт: прямой connect на loopback запрещён, а `*.localhost`
  совпадает с `localhost` в её `NO_PROXY` и в обход прокси песочницы не идёт. Команды, которым нужны адреса, — вне
  песочницы, браузер агента — вне её сам.
- С `sandbox.network.allowLocalBinding: true` (#396; правка действует в идущей сессии) команды в песочнице ходят на
  loopback: адрес задачи `*.localhost` через прокси отвечает 200 curl и `fetch` Bun, API прокси отдаёт маршруты,
  закрытый порт — `ECONNREFUSED` вместо `EPERM`; локальный порт и слушается. Нужна для того, чтобы агент открывал
  приложения задачи из песочницы и там же шли тесты, которые поднимают свой сервер на `127.0.0.1`; Docker она не
  открывает.
- `sandbox.excludedCommands` (Claude Code в приложении): правка настроек действует в идущей сессии; запись выводит
  вызов из песочницы, только если покрывает каждую его команду (`| head`, `; echo`, перенаправление в файл — нет).
  `docker compose *`, `docker ps *`, `gh *` работают; запись для скрипта (`bun <путь>/task-env.ts *`, с `~` и с
  абсолютным путём) — нет, хотя текст вызова совпадает. Поэтому скрипт агент запускает вне песочницы отдельным
  вызовом (`dangerouslyDisableSandbox`, через обычные разрешения), а `excludedCommands` — для прямых вызовов Docker.
- HMR приложения в контейнере с кодом из worktree: Vite 8.3 в `node:24-alpine`, worktree смонтирован в `/app`, Docker
  Desktop (движок 29.8), прокси на 80 — правка CSS на хосте дошла до страницы в Chromium без перезагрузки.
